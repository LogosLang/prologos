# BLOCKING

## `D3-B1` — [C · S · R · X] The silent-`<error>` class: PS8's "miss = loud" is incomplete over PS15's own subject list, and one instance launders fabricated presence into a sealable closed row

**Severity justification for BLOCKING:** PS8 is the settled spec's *completeness claim* about miss semantics; PS15 admits five subject classes; PS8 rules four. The fifth is silent AND type-level compounding. This is self-contradiction between two settled items plus a demonstrable unsoundness on a surface the design itself pulls in scope — not a deferral.

**Claim.** Four independent lenses found four distinct instances of one class: a read that misses returns a *well-typed* `<error>`/`none` value with **zero errors reported**. PS8 (:611-615) rules exactly four cases (closed-row miss · dyn-tail miss · PVec OOB · tuple OOB) and P2's prerequisite list (:55) names only "PVec loud OOB". Unruled and unlisted:
- **(a) `(Map K V)` miss** — PS15 (:645-648) admits it as a subject; PS8 never rules it; `record-project` is row-only so a Map subject never reaches a miss path at all.
- **(b) `map-get` on a nat row** — returns `none` while inferring the *position's* type. This is on the PS2 migration path: `tup[1]` works only via `expr-get`; the dot desugars to `expr-map-get` (macros.rkt:5488-5493) and the shipped multi-select is built entirely from `expr-map-get` chains (elaborator.rkt:2291-2294). **PS2 moves element extraction from `tup[1]` to `v.1`.** Implemented naively, that converts a working, test-pinned form into a silently-`none`-returning one.
- **(c) `List` OOB** — same hole as PVec; absent from §3.5's four-way table.
- **(d) the dyn-tail seal** — `sealed.a` → `<error> : Int` at 0 errors while `[validate Cfg m2]` → `err {:a missing-required}`. Static seal and runtime validator disagree on the same value.

**And the compounding step:** a Map miss can be minted into a CLOSED row asserting presence the source type never guaranteed — directly against PS15's "Selection results are ordinary closed rows — sealable, validatable, def-storable."

**Evidence — all four in ONE file, verified by me at 74ec6d02:**

```
0: m : [Map Keyword Int] defined.
1: <error> : Int            ;; [map-get m :zzz-not-present]
2: <error> : Int            ;; m.zzz-not-present
3: sel : {:got Int} defined. ;; def sel := {:got [map-get m :nope]}
4: {:got <error>} : {:got Int}
5: tup : ⟨Nat String Keyword⟩ defined.
6: "a" : String             ;; tup[1]        — correct (expr-get leg)
7: none : String            ;; [map-get tup 1N]
8: none : Nat               ;; [map-get tup 0N]
9: pv : [PVec Int] defined.
10: <error> : Int           ;; pv[5]
--- 0 errors ---
```

Mechanism: `typing-core.rkt:538` `record-project` destructures `(expr-Record-key-domain rec)` at :539 — every arm is row-shaped (:549 keyword, :559-563 nat literal, :564-575 dynamic/union); an `(expr-Map k v)` subject reaches none of them. Type side of (b) is right (`typing-core.rkt:557-562` F1a-col literal-index arm returns `(record-field-type fld)`); value side: `reduction.rkt:3065-3070` whnf's `expr-map-get` arm ends `[(definitely-not-map? m*) (expr-fvar 'none)]`, and `definitely-not-map?` (`reduction.rkt:1707-1735`) has no arm for the tuple's runtime representation — **the same walker gap §3.6 flags for `expr-broadcast-get`, firing on a second node.**

**Why the design looked right.** §3.5's four-way table is drawn from the ROW carrier and the shipped degenerate cases — exactly where a Path Selection audit would look, and all four entries are correct. `(Map K V)` slipped through because it is not a row (no presence marks, no tail, no support set) and entered from the *other* end, as one reassuring sentence in PS15. `map-get`-on-nat-row looks like an internal op, except the shipped multi-select §3.2 proposes to retype is built entirely out of `map-get` chains. And the whole class is invisible to a green suite: it reports zero errors and returns well-typed-looking values — the exact silent-wrong-answer signature `pipeline.md` § Exhaustive Walkers says a green suite cannot catch.

**Proposed resolution (information flow, not algorithm).** Make the miss ruling a function of **what negative information the subject's type actually carries** — the §4.11 asset applied where it belongs — rather than a per-subject case list:
- a **closed row** carries "lacks *l*" → error;
- a **dyn tail** carries "unknown" → D19 fresh meta;
- a **`(Map K V)`** carries *nothing* about presence → the honest result is the `Option`-shaped one the traits already return (§3.5's own closing sentence notes this), never a bare `V`;
- an **unbounded positional carrier** (PVec/List) carries no arity → the miss is a runtime fact, and PS8 must say so next to "loud".

Stated that way the fifth case falls out of the same rule instead of needing a table row, and PS15's sealability claim gains its required qualifier: *a selection result is a closed row only when its presence information was **sourced**, not fabricated.* P2's census must add the `(Map K V)` leg and the `map-get`-on-nat-row leg beside PVec OOB, and both must be pinned **failing-test-first** (walker-shaped; §8 R4 already prescribes this).

**Adjudication:** ☐ Accept ☐ Accept-problem-reject-solution ☐ Reject-with-justification ☐ Defer-with-tracking

## `D3-B2` — [R · X · P · C] PS11 is false as written: its sections do not lex, and its named remedy is unavailable

**Severity justification for BLOCKING:** PS11 is in §5.9, the consolidated spec implementation will be built from. Both of its operative claims are falsified by probe, and its "probe-verified" annotation is evidence of the wrong instance. A settled item built on a false premise must be re-opened before P5 opens against it.

**Claim.** PS11 (:625-631) asserts: "`.[sel]` ≡ `[fn [r] r[sel]]`; `.name` = the simple section … **Works in argument/application position TODAY (bidirectional checking, probe-verified)**; standalone `def sel := .[…]` inherits the standalone-lambda gap (**annotate**) — named, not hidden."

- **(i) The sections do not lex.** `rewrite-dot-access` folds a FLAT datum list left, consuming the PRECEDING element whenever the accumulator is non-empty. `map .name users` becomes `((map-get map :name) users)` — the section binds to `map`. `.[…]` is worse: the leading `.` lexes as a bare symbol and the bracket folds onto it. Whitespace cannot rescue it (the reader is positional). What WAS probe-verified is the explicit `[fn [r] r.name]` form, whose typing is fine — a different claim.
- **(ii) The "annotate" remedy is unavailable for the case it is named for.** An anonymous row is not a writable type in any annotation position. The remedy works only via a **named schema** (`def getn : <Person -> String> := [fn [r] r.name]` → 0 errors). For `.[sel]` over an anonymous row — the case the sugar exists for — there is no annotation to write.

**Evidence — re-verified by me at 74ec6d02:**

```
1: '["a" "b"] : [prologos::data::list::List String]   ;; map [fn [r] r.name] users  — WORKS
2: ((map-get map :name) users)                        ;; (expand (map .name users))
3: (map (get . name) users)                           ;; (expand (map .[name] users))
4: ERROR: Could not infer type                        ;; map .name users
--- 1 errors ---
```

`macros.rkt:5484-5491` (the fold); the `(if (null? acc) …)` guard is the ONLY thing between a section and absorption, and `acc` is null only when the sentinel is the datum's FIRST element. Standalone-lambda arms exist **only for `$dot-key`** (`macros.rkt:5455-5457`, :5474-5477, both gated `(= (length datum) 1)`) — `$dot-access` has none, so even `(expand (.name))` yields a raw sentinel, not a lambda. Reader: `".name"` → `(($dot-access name))`; `".[a b]"` → `((|.| ($postfix-index (a b))))`. For (ii): `def r : {:name String :age Int} := …` → `ERROR: Expression is not a valid type`; `spec f {:name String} -> String` → `Type mismatch`; `defn f [r : {…}]` → syntax error; repo-wide `grep -rn "\[fn \[[a-z]* : {"` over `.prologos`/`.rkt` → **zero hits**.

Migration hazard, live and unlisted: `"|> u .name"` → `(($pipe-gt u ($dot-access name)))` folds to the ACCESS reading. Any existing file where a `.field` access follows an unrelated symbol currently folds one way and would fold another after the fix.

**Why the design looked right.** PS11 was ruled in round 2 (Q_S9) when the spelling was `.[sel]`, then re-spelled in round 3 (PR-7) to `.name` — the re-spelling moved it onto a sentinel with different fold behaviour and the "probe-verified" annotation was carried forward unre-probed. Bidirectional checking of an unannotated lambda in argument position genuinely *does* work here, so the typing half is true, which makes the reader half easy to assume. And the `(if (null? acc) …)` guard makes the standalone case look fine in isolation — exactly the shape a quick probe takes. §3.4's own note that the adjacency test is "purely POSITIONAL (`end-pos == start-pos`)" is evidence FOR this finding and the doc never connects it to PS11. Note the document's §4.12 REFUSE list *names this exact trap* ("GHC disambiguates `.` from composition **by whitespace**") — the design lists the trap and steps in it.

**Proposed resolution.** (1) Strike "(bidirectional checking, probe-verified)" and replace it with what was measured: the meta-codomain/HOF case works; the section spelling does not exist. (2) A leading-dot section is a *left-boundary* fact the flat datum list has already erased — so the boundary must be carried by the token itself (the same conclusion §3.4 reached for `x.[a]`: "needs a token"), or by srcloc through the fold (`parse-reader.rkt:2471-2479`'s adjacency test already carries the positional information; the fold discards it). Either way this is **P3 reader work plus a migration census**, and neither is in the ladder — P3 lists `.N`/`.:.`/`.:[`/`*`/dot-key but not sections; P5 lists sections as *semantics*, as if the surface were already available. (3) Restate PS11's residual honestly: the remedy is *annotate with a named schema*; the anonymous-row case has no remedy and is `D3-S11`.

**Adjudication:** ☐ Accept ☐ Accept-problem-reject-solution ☐ Reject-with-justification ☐ Defer-with-tracking

## `D3-S1` — [X · R · C] PS10's `v.i` names the wrong prerequisite; the real work (soft name resolution at the elaborator) is budgeted nowhere, and "brackets are 100% literal/static" is false under its plain reading

**Claim.** PS10 says `v.i` "requires the P2 Int-gate fix". But whether `x.i` means field `:i` or index-by-`i` is decided by `rewrite-dot-access` at **preparse**, which converts the segment unconditionally to a keyword — so the `record-project` dynamic leg P2 repairs can never be reached from a dot. The feature *is* buildable (the escalation to "undecidable" was refuted: `typing-core.rkt:1843-1865` already passes the key through as a raw expression and lets the subject's type pick the arm, and its dynamic leg at :565 already branches on key domain). What is genuinely new and unbudgeted: the elaborator must emit ONE neutral key node, and the name lookup must be **SOFT** — an unbound `i` must not be an elaboration error when the subject is keyword-keyed. No phase carries this; §2's P4 parenthetical scopes itself to PS3–PS8. Sub-item: PS10's own sentence "brackets are 100% literal/static" is false under its plain reading, since PS3 admits arbitrary paths as selectors and `x[admins.i.name]` puts a dynamic navigation inside a bracket; the spec never says whether that is legal.

**Evidence.** `macros.rkt:5484-5491` — `` `(map-get ,target ,(string->symbol (string-append ":" (symbol->string field)))) `` — a KEYWORD, no type consulted; invoked from preparse at `macros.rkt:2488`. Staging: `driver.rkt:721` elaborate → `:735`/`:758` type-check; unbound names hard-error at `elaborator.rkt:817-819`. Probes: `(expand (x.i))` → `(map-get x :i)`; with `def i := 1` and `def m := {:i 99}`, `m.i` → `99 : Int` (field reading wins, the binding is not captured); annotated `spec pick2 [PVec Int] -> Int / defn pick2 [c] c.i` → `ERROR: Type mismatch` (annotation cannot rescue a reading fixed before elaboration). Coordinate drift while you're here: §5.2 CH-2 cites `elaborator.rkt:2301`; the quoted arm is at **:2297-2298**. §3.5/PS10 cite `typing-core.rkt:563-566` for the dynamic leg; it begins at **:564**, `key-ty` at **:565**.

**Why the design looked right.** §5.6 PR-3's argument is genuinely elegant and *semantically* sound — the key domains are disjoint by Q_B, so no value-level ambiguity exists. The flaw is not in the semantics but in WHERE the disjointness can be observed. §3.4 correctly established that `v[1.b]` "is NOT a reader problem" and "the lift is one fold arm"; PS10 generalized that optimism to the DOT path, where the payload is a symbol preparse must classify immediately. §2 P4's "core-elaborator form (NOT preparse)" reads as if the staging problem were solved — but the elaborator is still upstream of typing.

**Proposed resolution.** Express the segment as an *unresolved observation* rather than a lexing decision: preparse emits one neutral segment node carrying the raw symbol; the **key-domain fact flows from the subject's row cell** (already a component of the D13/Q_A carrier) into the segment's resolution, so the segment's meaning is DERIVED from the subject, not decided by token position. The soft/undecided name lookup is then the one new mechanism and must be a named P3/P4 deliverable, with QTT reading usage off the same resolved domain (per `pipeline.md` § infer/inferQ twins). Restate PS10's invariant over what assembly actually consumes: *every selector's contributed KEY is statically determined; the VALUE it navigates to need not be* — which admits `x[admins.i.name]` without weakening typability. If that is too much for v1, CUT `v.i`: Q_S1 already established `get`/`get-in` as the dynamic escape hatch, so the cut costs the design nothing it claimed.

**Adjudication:** ☐ Accept ☐ Accept-problem-reject-solution ☐ Reject-with-justification ☐ Defer-with-tracking

## `D3-S3` — [X · P · R · C] `*` fell out of PS3's structural-operator list; splat has no key, `^` cannot attach to it, and §5.7's showcase table is in the illegal spelling

**Claim.** Three consequences, one cause.
- **(a)** PS3 (:591-594) lists the structural operators as "(`:` or `[`)". Its ancestor PR-6 (§5.7 :497-498) read "(`*` or `[`)" — when round 5's PR-9 moved iteration from `*` to `:`, `*` was *dropped* rather than kept alongside. So `x[server.*]` is a "pure path" under PS3's own definition and keys by `*`, contradicting PS9's "fields spliced into the result level". `:*` is not even lexable (`parse-reader.rkt:511-516` gates `recognize-keyword` on `(char-alphabetic? c2)`).
