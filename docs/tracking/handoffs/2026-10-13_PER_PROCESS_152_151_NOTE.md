## 152 ✅ `process-file` forced two major GCs per call — `0e5da30f`

**What it was.** `measure-memory-before`/`-after` ran `(collect-garbage 'major)` on every call
of three functions: `process-string-inner` (`driver.rkt:2462/2482`), `process-surfs`
(`:2689/2709`) and `process-file-inner` (`:2813/2869`). That covers every test `run`, every LSP
re-elaboration and every `racket driver.rkt FILE`. Module loading is not affected:
`load-module` calls `process-command/solve-guard` directly.

**What changed.**
- `performance-counters.rkt:423` adds `current-memory-stats?`, a parameter defaulting to `#f`.
- `:425` adds `memory-stats-enabled?`: the parameter, **or** `PROLOGOS_MEMORY_STATS` set to
  anything but `""` or `"0"`. It reads the variable through `getenv` on each call, so a
  `putenv` after the module is loaded still counts.
- `measure-memory-before` (`:433`) returns `#f` and collects nothing when the gate is off.
- `measure-memory-after` (`:443`) returns `#f` when `before` is `#f`. The decision is taken
  once, so a pair of measurements is never half done.
- `print-memory-report!` (`:455`) prints nothing for `#f`.
- The driver CLI gains `--memory-stats` (`driver.rkt:3917`); the CLI comment at `:3906` is
  updated.

**What MEMORY-STATS prints when not measuring: nothing (omitted, not marked).**
- Without the forced GC the fields mean something different: `mem_retained_bytes` would
  include garbage, and the heap level would depend on when a collection last ran.
- `batch-worker.rkt:374` stores the **last** MEMORY-STATS line of each file as the `memory`
  field in `timings.jsonl`. A record that looks the same but was not forced would silently
  change the meaning of that history and of the `benchmark-tests --report` and
  `benchmark-report.rkt` memory charts.
- An absent line is detectable, and every consumer already handles it:
  - `batch-worker.rkt:374` (`(and (not (null? memory-entries)) …)`);
  - `bench-lib.rkt:188` (`#f`);
  - `benchmark-tests.rkt:319` (`(hash-ref r 'memory #f)`);
  - `benchmark-report.rkt:269` (`hash-has-key?`).

**`pipeline.md` §New Racket Parameter.** The parameter is only ever *read*, or bound with
`parameterize`, and nothing assigns it at module level. So it needs no `test-support.rkt`
entry (the default is the wanted value) and no batch-worker save/restore entry (a test cannot
leak a value). It is not meta or speculation state. Two-context audit: module loading never
measures, and inside `process-*` the gate is read once per call.

**Tests.** `tests/test-memory-stats.rkt` has 6 cases. Every case runs in a copy of the

## 151(a) ✅ `pnet-stale?` read the whole file for a 2-element header — `7358c7c4`

**What changed** (`pnet-serialize.rkt`):
- **`PNET_VERSION` 10 → 11** (`:201`). The comment block at `:191-200` follows the
  version-gate rules at `:107-188`: a FORMAT change, exact equality, every cache regenerates
  once.
- **File layout.** A file is now two data: the header `(pnet-header VERSION SOURCE-HASH)` and
  then the body, which holds the old slots 2–30 unchanged. `serialize-module-state` writes
  them separately (`:894`, `:935-938`) inside the same atomic temp-file + rename.
- **`read-pnet-header`** (`:211`) first peeks for the 13-byte prefix `#"(pnet-header "`
  (`:207`) and only then calls `read`. An old single-datum file (`(10 …`) or garbage is
  rejected in O(1) without parsing, and on success the function consumes exactly the header.
- **`pnet-header-fresh?`** (`:223`) is the staleness judgement, the same as before: exact
  version equality and an equal source key.
- **`pnet-stale?`** (`:832`) now reads only the header.
- **`deserialize-module-state`** (`:943`) reads header and body in one pass. It reassembles
  `(list* version key body)`, which is the v10 `raw` layout, so the slot-decoding code below it
  is untouched.
- `PNET_VERSION` and `read-pnet-header` are exported for tests.

**Staleness semantics.** For every well-formed file the judgement is identical: the file must
exist, `infrastructure-stale?` must be false, the version must match exactly and the source
key must be equal.

The one difference: `pnet-stale?` no longer notices a **corrupt body** under a valid header. The
loader still rejects such a file and returns `#f`, so `load-module` (`driver.rkt:3016-3020`)
falls back to source elaboration exactly as before. The only callers of `pnet-stale?` are
`load-module` and tests. The atomic rename makes a corrupt body unlikely in practice.

**Tests.** `tests/test-pnet-header.rkt` has 12 cases on a temp `:no-prelude` module, using the
`test-record-pnet-cache.rkt` fixture:
1. the layout: header prefix, 3-element header, exactly 2 data, 29-slot body;
2. fresh;
3. cache-hit round trip: results equal the source run, and the file is not rewritten;
4. `deserialize-module-state` returns 28 slots and the exports equal the written body's;
5. a valid header over an unreadable body: `pnet-stale?` is `#f` (header only) and the loader
   is `#f` (no raise);
6. stale by source mtime: both readers refuse it, and restoring the mtime makes it fresh again;
7. version gate: v10, v12, `"11"` and `'eleven` are all stale with no crash;
8. **a v10 single-datum file with the CURRENT source key** is stale with no crash, as is a v10
   file with an unclosed body;
9. degenerate files (empty, truncated header, wrong arity, garbage, unparenthesized);
10. the prefix peek consumes 0 bytes on an old file and exactly the header on a v11 file;
11. a load over a v10 file falls back to source and **regenerates a v11 file**;
12. run 1 writes the cache.

## Open questions

1. **Runner opt-in for MEMORY-STATS.** Which of (A) default-on with records unchanged,
   (C) a `--memory-stats` flag, or (B) per-file measurement in batch-worker? The tradeoff is
   the per-call record vs about 29 ms × 2 per `process-string` in every suite file. I lean (C).
   Another agent owns the runner right now, so the patch may need re-basing onto its changes.
2. **151(b).** Fasl body or retire the cache? The numbers above favour fasl (inferred warm load
   ≈ 310 ms vs no-cache ≈ 560 ms). The next step is one end-to-end measurement.
3. **Equal?-keyed registries round-trip as `hasheq`** (`pnet-serialize.rkt:341`, `:794`).
   `restore-registries!` (`driver.rkt:2954`) folds the delta into the parameter's own
   equal?-hash, but the cell write passes the `hasheq` delta through as is. I did not examine
   whether a cell-primary `subtype-pair?` lookup (`macros.rkt:8084`, a fresh `cons` key) hits
   after a cache load. The existing `test-pnet-registry-restore.rkt` covers restore by counts
   and selected registries. UNVERIFIED and out of scope; a candidate to file if someone
   confirms a miss.
4. `infrastructure-stale?` (`pnet-serialize.rkt:826`) invalidates every cache on each
   `driver_rkt.zo` rebuild. That is correct, but it means a developer pays a cold load after
   every compiler edit. This bears on (b), since the cache's benefit only shows on unchanged
   builds.
