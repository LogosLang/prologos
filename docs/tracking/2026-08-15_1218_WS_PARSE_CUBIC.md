## 1. Why nobody noticed

`parse_ms` is defined in `performance-counters.rkt` (`phase-timings-parse-ms`,
and a `parse` case in the `time-phase` macro) — but **`(time-phase 'parse …)`
has ZERO call sites**. The counter reports `0` for an 828-line file, and `0` is
indistinguishable from "fast". It was printed on every benchmark run for months.

I nearly reported "the parse is free" on the strength of it. Same fail-open
shape as `core.hooksPath`, the audit template's dead anchor, and the stale
grammar: **a mechanism that never fires looks exactly like one that works.**

## 2. The diagnosis — two quadratic loops, one dominant

Both live in `build-tree-from-domains` (`parse-reader.rkt:1769`). Profile:
that function is **97.2% of parse total, 85.4% SELF**, with `find-line-start-pos`
the only visible callee at 12.1%.

### Loop 2 — `find-content-line-for-pos` (the 81%)

```racket
(define (find-content-line-for-pos pos line-boundaries n-lines)
  (let loop ([i (- n-lines 1)])
    (cond [(< i 0) 0]
          [(<= (list-ref line-boundaries i) pos) i]   ; <-- list-ref is O(i)
          [else (loop (- i 1))])))
```

`line-boundaries` is a **list** (built by `for/list`), so `list-ref` at index `i`
is **O(i)**; the loop scans **backwards from `n-lines-1`**, so a token on line `k`
costs Σ ≈ O(L²) with L the line count. Called once per token, and T ∝ L, giving
**O(L³)**.

⚠ It does **not appear in the profile** as its own entry — it is small enough that
Racket CS **inlines** it, so its cost is reported as `build-tree-from-domains`
self time. That is why the profile alone could not finish the diagnosis, and why
the narrow test was necessary.

**Narrow test** at the real shapes of `conversions.prologos` (L=828, C=26546,
T≈3757), replicating the loop verbatim:

| variant | time |
|---|---|
| `list-ref` backward scan (as shipped) | **873.6 ms** |
| vector + binary search | **0.3 ms** |

873.6 ms of a measured 1073.2 ms total parse = **81%**.

### Loop 1 — `line-boundaries` construction (the ~12%)

```racket
(for/list ([li (in-range (rrb-size content-line-indices))])
  (find-line-start-pos char-rrb (rrb-get content-line-indices li)))
```

`find-line-start-pos` walks **from position 0** counting newlines, once per line
→ **O(L × C)**, with every character access an `rrb-get` on an RRB tree. One
forward pass recording each line start makes it O(C).

### The measured curve (warm, best of 3, all verified to complete)

| bytes | lines | parse |
|---|---|---|
| 742 | 11 | 0.3 ms |
| 5,215 | 179 | 8.6 ms |
| 7,975 | 192 | 12.1 ms |
| 9,964 | 240 | 28.2 ms |
| 26,546 | 828 | **1073.2 ms** |

5.1× the bytes → 125× the time; exponent ≈ 3.0.

⚠ **Scope, RESOLVED.** This was first recorded as possibly measuring a path
production does not use. The chain is now traced end to end and **both** WS
entry points reach it:

```
process-string-ws ─┐
                   ├─> merge-preparse-and-tree-parser ─> read-to-tree
process-file (ws) ─┘        (driver.rkt:2537)            (parse-reader.rkt:2229)
                                                              │
                              build-tree-from-domains <── parse-string-to-cells
```

I briefly concluded the opposite — a grep for callers of `parse-string-to-cells`
showed only `parse-reader.rkt` itself and tests, and I dismissed the in-file hit
at `:2229` as internal. It is `read-to-tree`, the production entry. Recorded
because the same grep will mislead the same way next time.

## 3. P4 is not optional bookkeeping

Wiring `(time-phase 'parse …)` is what stops this recurring. A perf defect that
is invisible to the project's own instrument will come back, and the next person
will also read `parse_ms: 0` as good news.

---

## 4. Correctness stance

This is a **pure optimization**: the parse output must be **identical**, not
merely equivalent. P3 is therefore a differential gate — run both
implementations over the corpus and assert equality — following the
"differential oracle" pattern in `.claude/rules/pipeline.md` § Exhaustive
Walkers. A faster parser that changes one tree is a regression, not a win.

<a id="results"></a>
## 5. Results

### The fix

Two edits in `parse-reader.rkt`, both in `build-tree-from-domains`:

- **`compute-line-starts`** — one O(C) walk producing a vector of every source
  line's start, replacing L separate `find-line-start-pos` calls that each
  rescanned from position 0. `find-line-start-pos` is **retained** as the
  differential oracle and is now documented as not-for-production.
- **`find-content-line-for-pos`** — binary search over a **vector**, replacing
  the backward linear scan with `list-ref` (O(i) per probe) over a **list**.

### Measured (warm, best of 3, every run verified to complete)

| bytes | before | after | |
|---|---|---|---|
| 742 | 0.3 ms | 0.3 ms | — |
| 5,215 | 8.6 ms | 1.6 ms | 5.4× |
| 7,975 | 12.1 ms | 2.9 ms | 4.2× |
| 9,964 | 28.2 ms | 3.6 ms | 7.8× |
| 26,546 | **1073.2 ms** | **10.5 ms** | **102×** |
| 28,523 | 1688.6 ms | **10.9 ms** | **155×** |

**The curve is now linear**: 38× the bytes costs 36× the time, against an
exponent of ≈3.0 before.

### Correctness — and the pin was mutation-tested

Four contract tests in `tests/test-parse-reader.rkt` assert each fast form
against the slow form it replaced, over **real corpus files** (not toy strings):
line starts agree at every line *including past the end*; line starts are
strictly ascending (binary search's precondition, which would otherwise fail
SILENTLY); binary search agrees with the backward scan at ~400 positions per
file; and empty/newline-only inputs are unchanged.

⚠ **Two traps caught while writing them, both of which would have made the pin
worthless:**
1. The corpus helper used a **cwd-relative** path that resolves from `tests/`
   but not from `racket/prologos`. The batch worker's cwd decides which — so the
   corpus could silently be EMPTY and all four tests pass **vacuously**. Now
   `define-runtime-path`, plus an explicit non-empty assertion.
2. A green run proves nothing on its own, so the pin was **mutation-tested**: an
   off-by-one in the binary search (`mid` → `mid-1`) makes it **FAIL**. Restored
   and re-verified clean.

### P4 — the counter, and why the obvious wiring was wrong

`time-phase! parse` at the `read-to-tree` call **compiled, ran, and still
printed 0**. It writes to `(current-phase-timings)`, but the parse completes
*before* the reported `phase-timings` struct is created and parameterized —
`process-file` builds `surfs` first and `pt` afterwards, and `process-surfs`
receives surfs already parsed. It would have been a second dead counter dressed
as a fix. The elapsed time is now stashed in `last-ws-parse-ms` and stamped into
`pt` at all **3** reporting sites.

Verified alive and proportional: io.prologos (742 B) 0 ms · eq.prologos
(5 KB) 5 ms · conversions.prologos (26 KB) 15 ms.

### P5 — regression gate

Full suite `--all --force-rerun`: **10224 tests, 488 files, 0 failures**, 180.9 s,
exit 0.

The relay-note baseline for the same invocation was 10217 tests in **197.0 s**
(the +7 are this track's contract tests). A ~16 s drop is consistent with every
WS-parsing test paying less — but suite wall time drifts with ambient load, and
`.claude/rules/testing.md` is explicit that a single pair of wall times is not
an A/B. **Treat it as suggestive, not established.** The load-bearing numbers
are the per-file parse measurements in the table above.
