## 1. What Was Built *(Q1, Q2)*

F1b delivered the record-typing **cornerstone** of CIU Track 6: an anonymous `Map` literal now *is* a structural record, a named `schema` seals a `Map` at four elaboration boundaries through **one** comparison engine, and a first-class `validate` face turns schema conformance into a recoverable `Result` at runtime. The arc ran ~2 implementation days (2026-07-17→19), 65 commits, with the full suite green at every commit (8687→8917 cases, 0 failures).

The architectural spine is **reuse, not addition**. F1b added **zero propagators and zero cells** (§13.7 Network Reality Check, verbatim: *zero propagators / zero cell-writes / no trace*). The seal projects a schema to a keyword row (`schema->row`) and delegates to the F1a row-comparison engine; width discharge, presence marks, and the seal residual all instrument the *same* arms. Validate is a single dedicated AST node (`expr-validate`) with **one** typing rule (`Result S E`) and **one** reduction arm that tabulates presence → fill → witness → `:check` → a collect-all failure map. The `:check` panic bridge (`wrap-schema-checks`) was *deleted* and re-expressed as `validate∘expect-valid` baked into the constructor doors — one engine, structurally, not two mechanisms maintained in parallel.

The originally-planned ladder was six slices + close (one D-ruling each: D25 echo, D26+D23-groundwork route-soundness, D21+D24 grid amendment, D22 seal, D27–D29 validate, D23 posture flip). **The scope evolved once, mid-arc**: after F1b.6, an adversarial stress-test battery (`wf_9e4a15ad`, ~120 probes) surfaced **one soundness bug + a cluster of record-type usability edges**, and the owner ruled an entire unplanned hardening phase (F1b.7, seven edges) in-scope before close — F1b.close was made *gated* on 7a because the cornerstone "correct in principle" claim depends on `:check` not silently accepting invalid data.

**User-facing WS example** (from `examples/2026-07-17-ciu-t6-f1b5-validate.prologos`, self-verified 28/28):
```
schema Person
  :name String
  :age Int

schema Cfg
  :host String :default "localhost"
  :port Int :default 8080

require [prologos::data::result :refer [Result ok err ok? err?]]
require [prologos::data::reason :refer [Reason missing-required check-failed
                                        type-mismatch unexpected-field errors-to-list]]

def m := [map-assoc [map-assoc {} :name "alice"] :age 30]
[validate Person m]        ;;=> ok … : Result Person (Map Keyword Reason)   ; a def-bound dyn row validates
[validate Person bad]      ;;=> err with structural field identity (map key) + expected/got
[validate Cfg {}]          ;;=> ok {:host "localhost" :port 8080}           ; DEFAULTS FILL at runtime (M2 debt discharged)
[map [validate Person _] rows]                                             ; the HOF beat (_ subject in scope)
```
On the seal side the same schema is a static+runtime gate: `def cgood := [Checked {:name "fred" :age 5}]` commits, while `[Checked {…:age 0}]` (schema `:check (> _ 0)`) errors at commit with a byte-parity message — `:check` now delegating to `validate` under the hood.

## 4. Bugs Found and Fixed *(Q6)*

The arc's headline defect is a **soundness bug the entire F1b.4/F1b.5 build missed** and only a deliberate adversarial stress-test surfaced.

### 🔴 HIGH — 7a: `:check` silently passes any non-Bool predicate (`f5aaae0b`)
`schema EqInt :n Int :check (eq? _ 7)` → `[validate EqInt {:n 8}]` returned `ok {:n 8}`, and `def bad := [EqInt {:n 8}]` **committed the violating value**. **Contributing factors** (multi-causal): (1) the check-pred was baked `elaborate`-*only* (no `check`/`resolve-trait-constraints!`), so a trait method (`eq?`) stayed a *stuck application* and a `[fn …]` check reduced to a function value; (2) the tabulate arm treated "not `false`, not `panic`" as **pass** — its comment *"true OR stuck (skip per err-polarity) → passes"* **mis-applied** err-polarity, which governs TYPE-witnessing (never-false-fail a field the seal accepts), to `:check` evaluation (a user runtime assertion, which must be LOUD when unevaluable). **Why the wrong path looked right**: err-polarity's "skip stuck" is genuinely correct for type-witnessing, so reusing it at the `:check` arm read as consistent — and it was *masked* because every acceptance/test marker used `(> _ 0)`-style checks (which `normalize-check-pred` maps to dict-free `lt`/`le`, never hitting the stuck path). **Fix**: a fail-closed four-way tabulate (no-pred→pass · panic→propagate · `expr-true?`→pass · `expr-false?`→check-failed · **else → new `check-unevaluable` Reason, reject**).

## 5. Design Decisions and Rationale *(Q5)*

Each decision traces to a design principle.

1. **Validate is a NODE, not surface code** (D27). A dedicated `expr-validate` carrying a baked per-field plan, ONE rule, ONE arm. *→ Correct-by-Construction*: the M2 refutation showed *any* surface-code tabulation re-creates a value/type mismatch under branch unification, so making validate a node makes "the M2-refuted class unrepresentable." Secondary *→ Data-Orientation*: the plan payload is simultaneously the future broadcast-item shape for on-network retirement. Alternative A1 (a surface stdlib form) was killed on principle in the options panel.
2. **E = `Result S (Map Keyword Reason)`** with a nominal closed `data Reason` (D27.3). *→ Spec-as-Living-Interface + the D13 pin*: a row-leaf error type is spec-inexpressible (rows are inferred+displayed, not parsed), so dogfooding lives at the AGGREGATE — the failure *map* is genuine F1 Map machinery whose hash-union join *is* the request-accumulator shape. `Path` keys wanted but the p0 probe fired the named `Keyword` fallback (Path-as-key is F-carrier work; the E *type* never breaks, only key *values* widen).
3. **The err-polarity witness + the D28 polarity table** (D28). A subsumption-aware table that *consumes* `subtype?` (the acceptance set IS the subtype closure), tier-1/2/3 coverage, test-locked *before* the typing rule. *→ soundness (never false-fail) + mirror-drift cap*: the live risk is err-polarity — a predicate-exact witness would FAIL Nat⊂Int data the seal accepts. Consuming `subtype?` rather than hand-rolling a parallel table is the anti-drift outcome. (This same invariant, *mis-applied to `:check` eval*, is what 7a later had to disentangle — see §6.7.)
4. **FULL DELEGATE + bridge deletion** (D29). `wrap-schema-checks` + its sole call site deleted in-slice; `validate∘expect-valid` baked into the doors' existing `let`-skeleton. *→ decomplection + Belt-and-Suspenders + Validated≠Deployed*: keeping both the old bridge and the new node is the exact belt-and-suspenders anti-pattern the rules flag as blocking; "never both live at close" drove the in-slice deletion, not a deferral. Byte-parity language deliberately *demoted* to parity-on-single-failure — an honesty discipline.
5. **The D23 narrow 2-kind partition + type-local walk** (F1b.6). The escape-boundary hard error fires only for {`dyn-row-projection`, `dyn-row-dynamic-projection`} escaping into a stored type, via a type-*local* walk — not all 10 dyn-row kinds, not a global sweep. *→ soundness without over-fire + design-wording fidelity*: the audit's counterexample (f1b3-width's `update-in` marker MUST keep scrubbing) forced the narrowing; type-local matches D23's exact wording and avoids over-firing on an intermediate meta discarded before the stored type.
6. **The 7c commitment-door decision** — def-commit is a commitment, mid-expr `the` is a view. *→ reuse of an existing posture*: the commitment-vs-view line *already exists* in code (`check-escaping-projection-metas` fires at exactly the two def-commit boundaries and nowhere else), so 7c *extends* the D23 "a stored type is a commitment" principle to `:check` rather than inventing one.
7. **Plan-as-data — widen the plan ENTRY, not the struct** (s4). Selection-validate rode a 7th per-field plan slot (`required-on-miss?`) rather than a 6th struct field. *→ Data-Orientation + zero-positional-break*: a struct field breaks four positional match/ctor sites + pnet-serialize; a plan slot breaks none (all bind `plan` opaquely; schema plans set `#t` → byte-identical). The general F1b posture applied to the extension boundary.

## 6. Lessons Learned — Evaluative + Meta

### 6.1 What went well *(Q5)*
1. **The grounding-audit → R-lens → owner-dialogue rhythm — the single highest-value finding.** A slice-opening mini-audit refuted or re-scoped a design premise on nearly every slice, *before code* (F1b.2a rewrote the route-soundness charter; F1b.4 found the "dead" map-empty arm was live; F1b.5-s2 "earned its keep three times"; **F1b.7 was 7-for-7**). See §6.4.
2. **The adversarial options-panel killed weak options on principle before any code.** Validate's mini-design (`wf_49cd3f40`, 5 clusters vs DESIGN_PRINCIPLES.org) killed A1 surface-code, the row-leaf-E, C1-refuse, C-gen, and D1-additive — leaving the node + the polarity table.
3. **Plan-as-data / names-as-data encoding** — extend the engine without struct/pnet churn (§5.7; also `check-unevaluable`/`default-unevaluable` as index-8/9 names-list appends → zero pnet touch).
4. **Demo-driven dogfooding found the real bugs the marker-driven suite structurally could not.** The 🔴 HIGH `:check` bug surfaced only via `foray.prologos` hand-testing + the adversarial battery (~120 probes, every finding main-session reproduced) — the acceptance suite was blind to it by construction.
5. **Census-before-behavior-change** — every door-strengthening flip (7a, 7c, 7d, 7g, s3b) ran a repo-wide census proving zero live GREEN markers flip, because the gap was untested-because-unused.

### 6.3 Where we got lucky *(Q7)* — stated without softening
1. **The all-`(> _ 0)` acceptance suite MASKED the 7a soundness bug for the entire F1b.4 + F1b.5 build.** The stress-test *battery* was discipline, not luck — the **luck is that no real invalid data leaked through a shipped surface before the battery ran**, on a feature whose whole claim is "correct in principle." Had the demo pinned a trait-method check first, the cornerstone claim would have shipped false.
2. **The owner-WIP tree made the naive close-bench unsafe — and the discipline to catch it already existed.** The perf-worktree `--ref` form (from the §12.7 F1a.2-p3 incident, where a false +9–19% was diagnosed as ambient) protected the F1b.close bench matrix. Lucky the false lead appeared at a low-stakes sub-close rather than corrupting the whole-arc baseline.
3. **The bench missing-`cd` self-correction.** The first nat-arithmetic counter-probe measured the baseline compiler *twice* and mis-attributed the +60-unit mover to `definitely-not-map?` (reduction); re-run under correct dirs, `reduce_steps` hadn't moved — it's entirely infer/unify. A wrong root-cause attribution would have shipped in this PIR.

### 6.4 What surprised us *(Q8)*
1. **The mini-audit REFUTES-ITS-OWN-PREMISE pattern — 7/7 across F1b.7, ~11 across the arc.** Every F1b.7 opener's framing was refuted or re-scoped by its grounding audit before code (7a root deeper; 7b monomorphic-not-trait; 7e a missing arm, not a subtype gap; 7g a sole-outlier drift; 7f one visible reject site; 7d/7c confirmed-but-rescoped) — plus F1b.2 (pinned fix-shape unrealizable), 4b (M2 refuted), D27 (subsumption claim refuted), F1b.6 (partition narrowed). The surprise is *how consistently* the design's own enumeration under-counted or mis-framed when ground against HEAD — this became the load-bearing rationale for the end-of-arc process formalization.
2. **Two probe SELF-corrections** (a probe that initially lied): the 7c compound-RHS double-wrap; the bench missing-`cd`. A probe is evidence, but a probe can mis-read its own output — the counter-probe / re-probe-both-routes discipline is what catches it.
3. **The map-empty-vs-schema arm was LIVE, not dead** — it was the recursion base case + always-on QTT twin, and its base `#t` *was* the width-partial blanket-accept hole. So the "loud retirement" and "THE FLIP" turned out to be the *same* commit (4e) — the co-land constraint solved itself.

### 6.5 How the architecture held up *(Q9)*
**The AST pipeline absorbed the whole validate feature as one node with no strain.** `expr-validate` threads all 12 stages cleanly (verified at HEAD: syntax ×9, subst ×2, zonk ×3, reduction ×6, pretty-print ×6, pnet-serialize ×1 [`regN!` same-commit], typing-core ×2, qtt ×1, + surface/parser/elaborator; tree-parser 0 because WS attaches via the datum-parser bail-list). The strongest signal: **s2 was FIRST GREEN 20/20 on the first full-pipeline run**. **The Network Reality Check is honest**: F1b added zero propagators / zero cells (grep-verified), and the off-network validate mass is named as *one row* in the §13.7 ledger with its own runtime-retirement horizon — never free-riding the typing rows. Only **pre-existing latent gaps** needed repair (the field-type class; the 7e schema-fvar→row projection), not new architecture; one genuine constraint (the type-lattice→reduction cycle) forced a clean module split (`field-type->witness-tag` in typing-core, `field-witness.rkt` below reduction).

### 6.7 What we learned about the problem *(Q14)* + are we solving the right problem *(Q15)*
**The err-polarity invariant has two faces with *opposite* polarities, and conflating them is the deepest domain hazard.** Accept-on-uncertainty is *correct* for TYPE-witnessing (never false-fail Nat⊂Int data the seal accepts → a stuck/unknown witness SKIPS) but *unsound* for `:check` evaluation (a user runtime assertion that can't reduce to a Bool must be LOUD, fail-closed). The 7a bug was precisely this mis-application. Two uncertainty polarities for two faces; the code must keep them distinct. Secondary domain lessons: fill is type-directed (the M2 boundary — value-materialization and type-assertion are separable); a selection is a read-side view; the nested boundary is one-level with structural depth symmetry.

**Are we solving the right problem?** The owner's framing — get records/`Map`↔schema **correct in principle** first, and Path Selection + solve ergonomics *fall out* as consumers — was validated on three counts: (1) the type substrate is genuinely *reused* downstream — the Rel master (written this close) states typing solve's solution rows reuses the F1 row carrier + presence machinery "(now complete)", and the typed-solution-rows charter physically *moved* from CIU into Rel; (2) the owner gated the close on 7a *because* it threatened the cornerstone — the framing was load-bearing in scope decisions, not just retrospective; (3) the demo beat (external-data → validate → Result) runs. **Honest counter-notes**: the bench measures *general*-program impact, not records-specific throughput (unmeasured); and the downstream payoff (Path Selection, typed solve rows) is *sequenced but not yet built* — the framing is validated as *a plan that held*, with the consumers still ahead.

### 8.4 What we'd do differently *(Q12)* — grounded, not hypothetical
1. **Seed the acceptance suite with a non-`(> _ 0)`-style `:check` marker from day one.** A single `:check (eq? _ 7)` or a lambda check at F1b.4/F1b.5 would have flipped 7a at *validate landing* instead of three sub-phases + a hand-testing arc later. 3. **Treat "fix these N instances" as a candidate CLASS, not a fixed count** — the "two field-type repairs" were a two-list-drift class; a full-list audit up front would have avoided four empirically-forced widenings.
4. **Gather a feature-specific microbenchmark (and an E2E measurement) at Pre-0, not just the general comparative suite.** F1b added D21/D22/D24 arms that fire *only* on record code, yet no records benchmark existed — so the feature's own cost was invisible until this PIR (§7/§12). ## 12. Open Questions the PIR Surfaces
- **The measurement gap was the largest oversight this PIR surfaced (owner-identified).** F1b's Pre-0 phase is *meant* to gather the microbenchmarks that guide the design — yet the arc shipped with **no records-specific microbenchmark and no E2E measurement of the delivered feature**; the whole-arc bench (§13.10) measured only *general*-program impact, so the D21/D22/D24 fast-path arms and validate's own runtime cost went unmeasured until this PIR forced them (§7, added post-close). Partial closure landed with this PIR — a records-path A/B (Δ≈0, records not regressed) + a feature-cost forward-baseline (validate is reduction-dominated) + two committed benchmark programs (`records-typing`, `records-seal-validate`) that put records *into* the standing comparative suite. **Still open**: (a) the demo's real shape — validate over an N-row list — has no throughput-vs-N curve (and validate's off-network tabulation is O(fields) sequential `andmap` with no broadcast, so the linear cost compounds; the on-network retirement horizon exists on paper but the crossover point is unmeasured); (b) more broadly, the lesson generalizes past benchmarking to **E2E feature testing** — Pre-0 should gather feature-specific microbenchmarks *and* an E2E measurement of the surface being delivered, not only algebraic/general-suite validation (→ §8.4, and the §10 distillation). This is the kind of design-vs-implementation-reality gap the PIR exists to name: the vision needs the *feature's own* performance and end-to-end behavior measured, not inferred from the general suite.
- **Undocumented critical knowledge**: the two-polarity err-polarity distinction (§6.7) lives in the 7a close-note + this PIR; until distilled (§10 PENDING), it's re-derivable only by re-reading the arc.
- **Process**: P-E (two-context boundary bugs) is codified yet *persists* across 6-7/10 PIRs + F1b — the 2026-05-17 recommendation for an *architectural* response (not more documentation) is now overdue; PM Track 12 (parameters→cells) is the named structural answer.
- **Are we learning from our PIRs?** F1b's own answer: the mini-audit-refutes-premise rhythm shows P-C/P-D maturing into a proactive tool rather than recurring as a surprise — single-loop (fix the bug) becoming double-loop (change the process that produced it).
