* Why We Track and Document Efforts

Language implementation is a long journey with compounding decisions.
Every design choice constrains future choices. Every bug reveals an
assumption. Every workaround reveals an abstraction gap. By tracking
lessons systematically, we:

1. *Avoid repeating mistakes* --- the same meta-variable pitfall doesn't
   bite twice
2. *Preserve institutional knowledge* --- when context windows reset, the
   lessons survive
3. *Inform future design* --- patterns that recur across subsystems
   suggest deeper abstractions
4. *Measure progress* --- timing data, test counts, and phase completions
   give concrete signals

* Workflow Lessons

** The Interactive Dynamic IS the Method (owner + Claude)

/Recorded 2026-07-25 (Rel T1 PIR). Six-plus instances; it recurs on nearly
every track, so treat it as a standing condition rather than a finding./

The owner holds a **large, persistent context and vision** that spans terrain
no single session can see. Claude can **tap vast knowledge and process text
rapidly** but cannot hold all the pieces together at once. Neither position is
sufficient alone, and the failure modes are complementary: Claude's designs
under-cover what only shows up when a human *uses* the language; the owner
cannot personally hold every coordinate, arm, and call-site the code actually
has.

What makes it work is **mutual challenge on honest ground**: assumptions named
and then probed, disagreements resolved by evidence rather than deference, and
both parties bound by the same principles. Concretely on Rel T1: ~45% of
production churn (the POL roster + the SUB spin-out) originated in owner
hand-testing, and the three largest scope changes — the POL roster expansion,
the B3 elevation, and the C.c redesign — all came from the owner. In the other
direction, main-session probing repeatedly refuted premises the owner and the
design shared.

**How to apply.** Treat a hand-testing pass as a **design input**, not a review
step. When the owner challenges scope, that is the process working, not scope
creep — capture it as a roster and sequence it. And when you disagree, say so
with evidence: the dynamic depends on both sides actually pushing.


For the full design-to-implementation lifecycle, see
[[file:DESIGN_METHODOLOGY.org][DESIGN_METHODOLOGY.org]] --- the five-phase process
(Research → Refinement → Design Iteration → Implementation → Composition)
that governs how we approach significant features. For how lessons are
extracted from completed work via Post-Implementation Reviews, see
[[file:POST_IMPLEMENTATION_REVIEW.org][POST_IMPLEMENTATION_REVIEW.org]].

** infer / inferQ Are Twins — a Missing Arm Makes the DIAGNOSTIC Lie

/Recorded 2026-07-25 (Rel T1 X.close Batch C). Three instances; the third was
live for a month./

`typing-core`'s ~infer~ and `qtt`'s ~inferQ~ must carry arms for the same AST
nodes. When only ~infer~ has one, ~inferQ~ falls to its catch-all, returns
~tu-error~, and ~checkQ-top~ reports a generic **"Multiplicity violation"** —
naming a subsystem that is working perfectly.

| Instance | Trigger | Missing arm |
|----------+---------+-------------|
| CIU T6 F1a.2 | ~def m0 := {}~ | map-empty |
| Rel T1 POL.5 | ~def x := solve (…)~ | goal-app head |
| Rel T1 Batch C | ~def m := {:f [fn …]}~ | standalone ~expr-lam~ |

**The diagnostic lesson (this is the one that saves the hour):** a
*"Multiplicity violation"* on a ~def~ whose body is **not** a lambda should be
suspected as an un-arm'd node **before** it is believed as a QTT result. Check
whether ~inferQ~ has an arm for the body's head node; ~infer~ almost certainly
does.

**Why it hides.** The def seam type-checks in CHECK mode, where lambdas and
many literals are canonical — so the bare form works and only the *infer*
position (a collection value, a goal argument) fails. Batch C's node looked
schema-specific for a month because it was first seen through ~validate~,
which merely *delegates* to its subject.

**The fix shape.** Add the arm; delegate the TYPE to ~infer~ (qtt's documented
"no drift twin" pattern) and mirror ~checkQ~'s corresponding arm for USAGE.
Structural direction, if this recurs a fourth time: give ~inferQ~ a generic
fallback so a missing arm degrades to *imprecision* rather than a false
failure — the `pipeline.md` § "Exhaustive Walkers" answer applied to the
typing pair.

** Phase-Gated Implementation
Break large features into lettered sub-phases (a, b, c...) with explicit
"done" vs. "remaining" tracking. This:
- Prevents scope creep within a single session
- Creates natural commit points
- Makes it easy to resume after interruption

** Tracking Documents Before Code
Create ~docs/tracking/YYYY-MM-DD_HHMM_TOPIC.md~ /before/ implementation.
Write down what you plan to build, what the phases are, and what success
looks like. Update after completion with lessons learned.

** Deferred Work Is Real Work
When something is deferred, immediately add it to ~docs/tracking/DEFERRED.md~.
Deferred work that isn't tracked is forgotten work. The DEFERRED file is
the single source of truth for all postponed tasks.

** Targeted Testing During Development
Run only affected tests (~racket tools/run-affected-tests.rkt~), not the
full suite. The full suite is for end-of-day regression. This keeps the
feedback loop tight (seconds, not minutes).

** Whale File Splitting
Test files exceeding 30s wall time bottleneck the parallel runner. Split
into ~-01~, ~-02~ parts with ~20 test-cases each. Check with
~racket tools/benchmark-tests.rkt --slowest 10~ after full runs.

* Type System Lessons

** Two-Phase Zonking
Intermediate zonking must NOT default unsolved metas --- it would commit
to wrong answers before all information is available. Only final zonking
(after type-checking completes) defaults metas to ~lzero~ / ~mw~.

This was a painful lesson: defaulting too early caused "spooky action at
a distance" where solving one meta would silently lock in defaults for
unrelated metas.

** Speculative Type-Checking
~save-meta-state~ / ~restore-meta-state!~ enables try-and-backtrack:
attempt a type check, and if it fails, restore the meta-variable store
to its prior state. Critical for:
- Church fold type inference (try fold interpretation, fall back to list)
- Union type widening (try homogeneous, widen if mismatched)
- Trait resolution (try one instance, backtrack to another)

** Dict Params Use ~:w~, Not ~:0~
Trait dictionary parameters must have unrestricted (~:w~) multiplicity.
If they're erased (~:0~), the body can't call the dict's methods at
runtime. This caused cryptic QTT violations until the invariant was
established.

** Meta Variables in ~infer-level~
Every AST node that appears in type position must have an ~infer-level~
case. When we added mixed-type maps, unsolved metas appeared in
~expr-map-empty~ type annotations, and ~infer-level~ had no case for
~expr-meta~. The fix: unsolved metas default to ~just-level(lzero)~,
matching zonk-final's behavior.

** Pattern Unification Boundaries
Miller's pattern fragment (the decidable subset of higher-order
unification) handles most practical cases, but higher-rank types push
beyond it. The workaround for higher-rank polymorphism: use explicit
~def ... : Type body~ instead of ~spec~/~defn~ when the type is too
complex for inference.

* Parser and Syntax Lessons

** Parser Keywords Are Sacred
Names like ~map-vals~, ~set-member?~ are parser keywords --- the parser
recognizes them at read time before name resolution. A library function
with the same name will be shadowed in unqualified usage. Solutions:
- Use qualified access: ~m::map-vals~
- Choose a non-conflicting name for the library function

** WS Reader ~$~ Is Quote
The ~$~ prefix in whitespace mode is the quote operator: ~$Foo~ desugars
to ~($quote Foo)~. It is NOT a sigil for variable names. This tripped up
dict parameter naming when traits were first implemented.

** Nested Bracket Arrow Syntax
~[B -> [K -> [V -> B]]]~ fails to parse (inner brackets create separate
argument groups). The flattened form ~[B -> K -> V -> B]~ works correctly.
This is a consequence of Prologos's uncurried convention.

** Consumer-Side Normalization
When special characters (~...~, ~>>~, ~|~) have readtable conflicts,
normalize on the consumer side (parser/elaborator) rather than hacking
the readtable. This is safer and keeps the reader simple.

* Trait and Instance Lessons

** Single-Method Trait = The Function
When a trait has exactly one method, the dict IS the function. No wrapper
struct, no field access. ~(Add Nat)~ resolves directly to the Nat addition
function. This gives zero-overhead dispatch for the common case.

** Instance Registration Is a Side Effect
~(imports [prologos::core::eq-nat :refer []])~ loads the module for its
side effect (registering the Eq instance for Nat). The empty ~:refer []~
signals "I don't need any names, just register the instances."

** Own-Definition Priority
When the user defines ~def map ...~ in their module, it shadows the
prelude's ~list::map~. This is intentional: user definitions always win.
Qualified access (~list::map~) remains available.

** Prelude Errors Are Silently Swallowed
~process-ns-declaration~ wraps module loading in ~with-handlers~ that
silently catches errors. When a prelude module fails to load, the only
signal is that its names are missing. This made debugging prelude changes
extremely difficult. Future improvement: log prelude loading errors.

* Collection and Library Lessons

** Map Can't Use Standard Traits
~Map K V~ has two type parameters, but ~Seqable~, ~Foldable~, and
~Buildable~ expect ~{C : Type -> Type}~ (one parameter). This is a
fundamental HKT limitation. The workaround: standalone functions in
~map-ops~ that operate directly on ~Map K V~.

** Type Constructors Aren't Terms
~(infer Add)~ doesn't work because ~Add~ is a type constructor (deftype),
not a term. To test type constructors, use a typed binding:
~(def x : (Add Nat) val)~.

** ~inferQ~ Returns Result Type
For AST keyword nodes (like ~expr-map-get~, ~expr-set-insert~),
~inferQ~ must return the RESULT type, not the input type. Getting this
wrong causes the QTT checker to track multiplicities against the wrong
type, leading to phantom violations.

** Library Function Names Don't Repeat Module Names
When ~prologos::core::map-ops~ exports ~map-keys-list~, the user writes
~m::map-keys-list~ --- "map" appears twice. Better: export ~keys~, user
writes ~m::keys~. This lesson drove the map-ops rename.

* Numerics Lessons

** ~expr->impl-key-str~ Must Handle All Types
The trait instance dispatch function must have cases for every numeric
type (~Int~, ~Rat~, ~Posit8~, ~Posit16~, ~Posit32~, ~Posit64~,
~Keyword~). A missing case causes silent dispatch failure with an
unhelpful error.

** Posit Widening Through Exact
Converting between posit sizes goes through exact rational:
~p16-from-rat (p8-to-rat x)~. This preserves as much precision as
the target format allows.

** Into Blanket Impl Pattern
~impl Into A B where (From A B)~ provides the reverse direction
automatically using parametric constraint resolution. This halves the
number of conversion instances needed.

* Homoiconicity Lessons

** Both Modes Must Produce Identical ASTs
The whitespace reader and the s-expression reader must produce
bit-identical ASTs. This is tested extensively and is a hard invariant.
Any divergence means macros behave differently depending on input mode.

** Quote Roundtrips Must Preserve Structure
~'[fn [x] [add x 1N]]~ must produce a ~Datum~ value that, when
reconstructed, yields the original expression. This is the foundation
for code-as-data metaprogramming.

** Quasiquote Comma Conflict
Racket's reader consumes commas before our readtable sees them. The
solution: a nested readtable (~prologos-qq-readtable~) that handles
unquoting within quasiquoted expressions.

* Architecture Lessons

** 14-File AST Pipeline
Adding a new AST node requires touching 14 files (syntax, surface-syntax,
parser, elaborator, typing-core, qtt, reduction, substitution, zonk,
pretty-print, and sometimes unify, macros, foreign). This is the cost
of a uniform AST representation --- but the benefit is that every
subsystem handles every node consistently.

** Callback Pattern for Circular Dependencies
When module A needs to call module B, but B already requires A, use a
callback parameter: B exposes a function that takes a callback, and A
provides the implementation at the call site. This avoids Racket's
circular require limitation.

** Sentinel AST Nodes
The reader emits sentinel nodes (~$dot-access~, ~$dot-key~, ~$pipe-gt~)
that are rewritten by preparse into standard AST forms. This keeps the
reader simple (it doesn't need to understand semantics) and the preparse
predictable (it transforms known sentinels).

* Optimization Lessons

** Prefer ~where~ Constraints for Specialization
When a function needs a trait constraint, use ~where~ syntax rather than
explicit positional dict parameters:

#+begin_src prologos
;; Good — eligible for call-site specialization:
spec my-fn {A} SomeArg -> Result where (Trait A)
defn my-fn [arg] where (Trait A)
  ...method-name arg...

;; Unavoidable but less optimal — invisible to rewriter:
spec my-fn [Trait A] A -> A
defn my-fn [dict x]
  Trait-method dict x
#+end_src

The ~where~ style threads the trait dictionary automatically via
~maybe-inject-where~ in ~macros.rkt~, and the ~rewrite-specializations~
pass in ~driver.rkt~ can replace calls with zero-overhead specialized
versions when the type argument is statically known. The explicit
positional dict style works, but the rewriter can't detect it.

** Call-Site Specialization: When to Add ~specialize~ Blocks
Rule of thumb:
- 3+ concrete types regularly used → add specializations for each
- Hot loop (propagator merge, inner folds) → specialize even for 1 type
- One-off generic usage → dict-passing overhead is negligible, don't bother

Each specialization is small (~4 lines: spec + specialize + defn + body)
and eliminates all dict-passing overhead for that type, collapsing to a
direct function call. The generic dict-passing version remains as the
correct fallback for types without a specialization.

** Two Dict-Passing Styles Coexist
The codebase has two styles for polymorphic functions that need trait
constraints:

| Style               | Example           | Rewriter sees it? | Ergonomics     |
|---------------------+-------------------+-------------------+----------------|
| ~where (Trait A)~   | ~new-lattice-cell~ | Yes               | Auto-injected  |
| ~[Trait A]~ positional | ~plus~, ~sum~   | No                | Manual at call |

Migration path for the positional style:
1. Change spec to use ~where~ clause
2. Change defn to use bare method names
3. Add ~specialize~ blocks for common types
4. Existing call sites continue to work (the desugared form is identical)

This migration is optional --- the positional style works correctly, it
just doesn't benefit from automatic specialization. Prioritize migration
for functions called in performance-sensitive paths.

* Meta-Lessons

** Completeness Over Deferral
When you have the clarity, the vision, and the full context --- finish
the work now. Half-built pieces that get deferred are half-built pieces
that get forgotten. The cost of re-acquiring context later almost always
exceeds the cost of doing the work while the understanding is fresh.

This doesn't mean never defer --- sometimes layering and phasing is the
only sensible approach. But the default should be: complete the solution.
Defer only when there is a genuine dependency on unbuilt infrastructure
or when the design is genuinely uncertain. "We'll come back to it" is a
red flag; if the work is clear enough to describe, it's clear enough to
do.

Corollary: when deferral /is/ necessary, it must be immediately tracked
in ~DEFERRED.md~. Deferred work that isn't tracked is abandoned work.

** Callbacks Are a Propagator-First Anti-Pattern

When a subsystem injects behavior across module boundaries via callback
parameters, it's a sign that the behavior belongs in the propagator
network, not outside it. Callback parameters are:
- Not correct-by-construction (they can be ~#f~; every call site must guard)
- Not data-oriented (the callback is an opaque function, not inspectable data)
- Not propagator-first (the callback fires imperatively, not through cell state)

The alternative: make the triggering condition a cell, and the response a
propagator that fires when the cell reaches the ready state. The module
boundary problem disappears because the propagator captures its closure at
registration time (in the module that has the resolution logic) and fires
at the appropriate stratum (in the network's scheduler).

Discovered during Track 6 Phase 8d: three callback parameters existed to
break circular dependencies between ~metavar-store.rkt~ and ~driver.rkt~.
Deep audit revealed them vestigial --- the stratified resolution loop was
the load-bearing path. The pattern: when you find callbacks in a propagator-
based system, ask whether the callback's trigger should be a cell and its
behavior a propagator.

** Let Pain Drive Design
Don't add features until they're needed. Every deferred item in
~DEFERRED.md~ was deferred because the pain wasn't yet sufficient to
justify the complexity. When the pain arrives, the solution is better
informed by real usage.

** Tests Are Documentation
The test suite (3000+ tests) is the most accurate documentation of what
the language actually does. When docs and tests disagree, tests win.
New features aren't done until they have tests.

** Grammar Is Living
~docs/spec/grammar.ebnf~ and ~docs/spec/grammar.org~ are canonical and
must be updated whenever syntax changes. Stale grammar docs cause more
confusion than no grammar docs.

** State Termination Arguments Explicitly
When adding a propagator or lattice to the network, state why it
terminates. "This propagator terminates because the lattice has height 3"
or "because type depth decreases on each cycle." If you can't state the
argument, the computation may not terminate. Fuel bounds catch bugs in
termination arguments; they should not BE the argument. See
[[file:GÖDEL_COMPLETENESS.org][GÖDEL_COMPLETENESS.org]] for the hierarchy of termination guarantees
(Levels 1--5) and the discipline for choosing the strongest available.

Discovered during Track 6/7 design: the stratified propagator network's
layered quiescence raised the question "what guarantees termination when
L2 feeds back to S0?" The answer required identifying a well-founded
measure (type depth × unsolved metas). Without stating this explicitly,
the design would have relied on fuel alone --- missing the structural
insight that makes the architecture provably decidable.

** Non-Equality Relations Break Equality Assumptions

When extending the SRE from equality-only to support additional structural
relations (subtyping, duality, coercion), every decomposition function
must be audited for equality-specific assumptions. Three classes of
assumptions were discovered in SRE Track 1:

1. /Lattice ordering assumption/: Equality uses a flat lattice where
   ~merge(Nat, Int) = top~ (incompatible). Subtyping needs a
   partially-ordered lattice where ~merge(Nat, Int) = Int~ (the
   supertype). Two orderings on the same carrier require separate merge
   functions --- a single merge cannot serve both relations.

2. /Symmetric decomposition assumption/: Equality decomposes with one
   descriptor (both sides have the same constructor tag). Duality
   decomposes with two descriptors (Send on one side, Recv on the other).
   ~sre-decompose-generic~ assumed symmetric decomposition; duality
   required a dedicated ~sre-duality-decompose-dual-pair~.

3. /Value copying assumption/: Equality safely copies the "unified" value
   to both sides (they converge to the same value). Duality and subtyping
   cannot --- copying source-side values into target-side sub-cells
   produces un-dualized or un-subtyped values. For non-equality relations,
   always initialize target-side sub-cells with bot and let propagators
   push the correct values.

When adding a new relation, analyze it along four axes before
implementation: (a) symmetry (symmetric, directional, involutive),
(b) merge semantics (merges cells, checks cells, swaps constructors),
(c) constructor mapping (same tag, dual tag pairs, coercion mapping),
(d) binder requirements (needs fresh metas, or operates on ground types).

Discovered in SRE Track 1 + 1B: 7 bugs total, 3 from equality-specific
assumptions. See [[file:../2026-03-23_SRE_TRACK1_PIR.md][SRE Track 1 PIR §4, §13, §14]].

** Retraction Is Aggregation's Dual
Both retraction (removing entries from a cell) and aggregation (collecting
the complete set of derivations) are non-monotonic operations. Both are
addressed by stratification: compute to fixpoint in a lower stratum
before the non-monotone operation in a higher stratum observes the result.
This insight from well-founded logic programming (NAF-LE) directly
informed the S(-1) retraction stratum design in Track 7. See
[[file:GÖDEL_COMPLETENESS.org][GÖDEL_COMPLETENESS.org]] § "Application to the Stratified Propagator Network."

** Data at Rest, Closures Derived on Demand

When persistent state contains closures (Racket procedures), serialization
fails. The fix is always the same: store the DATA from which the closure
can be deterministically derived, and derive the closure on demand (at
load time, at call time, or lazily).

This pattern appeared 6 times in PM Track 10's =.pnet= serialization:
1. /Foreign function procedures/ → store =(module-path . binding-name)=,
   re-link via =dynamic-require= at deserialize time.
2. /Preparse expander closures/ → store expander symbol name, look up
   in expander table at call time.
3. /Coercion functions/ → store =(coerce-via Sub Super via-fn-name)=,
   derive the closure from the coercion spec at deserialize time.
4. /Marshal-in / marshal-out closures/ → derive from foreign function's
   type signature (already stored as data in =source-module= +
   =racket-name= fields).
5. /Capability-wrapped foreign functions/ → store unwrapped reference,
   re-wrap with capability token pass-through at deserialize time.
6. /Gensym identifiers/ → store as tagged interned symbols (=symbol$$N=),
   reconstruct fresh gensyms from per-module table at deserialize time.

The general principle: registries and persistent state should hold DATA
REFERENCES, not closures. The closure is a CACHE — an optimization of the
data reference. If the data reference is lost (not serialized), the cache
cannot be reconstructed. If the data reference IS serialized, the cache
can always be re-derived.

This is Data Orientation applied to persistence: the serialized form IS
the NTT-correct representation. The live form (closures) is an
optimization cache derived from the data. When closures block
serialization, the data model is incomplete — the closure's provenance
(where it came from, what data generates it) is not recorded.

Discovered in PM Track 10: 22/40 prelude modules failed serialization
due to foreign function closures. The comprehensive fix (Option A:
embed provenance in struct) solved all 22 in one pattern. The
whack-a-mole phase (5 incremental fixes before the comprehensive audit)
demonstrated the anti-pattern: fixing ONE closure category at a time
reveals the next. The audit ("how many closure categories ARE there?")
broke the cycle.

See [[file:../2026-03-25_PM_TRACK10_PIR.md][PM Track 10 PIR]] and [[file:../research/2026-03-24_SELF_DESCRIBING_SERIALIZATION.md][Self-Describing Serialization Research]].

** Validated Is Not Deployed — Flip the Switch or Delete the Parameter

When new infrastructure is built alongside old infrastructure (hybrid
paths, dual pipelines, feature-flagged switchovers), a common pattern
emerges: the new path is validated (all tests pass) and the track is
declared complete — but the parameter controlling the switch defaults to
the OLD path. The new code runs in test configurations but never in
production. This creates four compounding costs:

1. *Invisible technical debt*: the old path can't be deleted because
   it's still the production default
2. *False confidence*: the track's PIR says "switchover complete" but
   the switchover is parameterized, not actual
3. *Deferred cleanup accumulates*: each subsequent track inherits
   the dual paths and must work around both
4. *Context loss*: when the switch is finally attempted (tracks later),
   the implementation context is gone and edge cases resurface

*The rule*: when a validation phase proves the new path works (full
suite GREEN), the NEXT phase MUST either (a) flip the default to the
new path and re-validate, or (b) delete the parameter entirely if the
old path is no longer needed. A parameter that defaults to the old
path is not a "safety net" — it's an admission that the switchover
isn't complete. Name it honestly: "Phase N: validated (not deployed)."

*Discovered in*: PPN Track 2 Phase 6g. ~use-tree-parser?~ validated
at ~#t~ (383/383 GREEN) but defaulted to ~#f~. The tree parser — the
entire point of the track — never ran in ~process-file~ or the default
~process-string-ws~ path. Three follow-on commits were needed to
clean up what should have been one phase: flip the switch, validate,
delete the parameter.

*Red-flag phrases*: "defaults to #f for safety", "validated but keeping
the old path as fallback", "can be enabled via environment variable",
"opt-in for now." These all mean: not actually deployed.

*Anti-pattern*: ~use-new-reader?~, ~use-tree-parser?~, ~use-propagator-X?~
parameters that default to ~#f~. Each one represents a completed
architecture that isn't running. The parameter itself is the debt.

** "Pragmatic" Is a Rationalization for Incomplete

When the word "pragmatic" appears in a design document or commit message
to justify keeping both old and new code paths alive, it is almost always
a signal that the Completeness principle is being violated. Audit the
specific claims:

- "The merge is a *pragmatic* bridge" → the new path can't handle all
  cases. What cases are missing? Can they be addressed in the current
  track? If not, is the gap explicitly tracked with a concrete plan?
- "A *pragmatic* approach is to keep preparse for X" → X is a
  responsibility not yet migrated. Is migration blocked by a genuine
  dependency, or by effort avoidance? Genuine dependency = acceptable
  deferral. Effort avoidance = Completeness violation.
- "The *pragmatic* path is ..." → rephrase as "the INCOMPLETE path is
  ..." and see if the sentence still feels acceptable.

*The test*: replace "pragmatic" with "incomplete" in every design
decision. If the rephrased sentence is alarming, the original decision
needs revisiting. If it's genuinely acceptable (e.g., "the incomplete
path is appropriate because X is blocked by unbuilt Track 4
infrastructure"), then the deferral is principled and should say
"deferred to Track 4 because [specific dependency]" not "pragmatic."

*Discovered in*: PPN Track 2 PIR analysis. The merge strategy was
described as "pragmatic" 4 times in the design doc. Rephrased: "the
INCOMPLETE path maintains two code paths because the tree parser doesn't
handle data/trait/impl." This reframing immediately clarifies that the
gap is the tree parser's form coverage, and the fix is extending it —
not accepting dual paths as an architecture.

*The discipline*: the word "pragmatic" is banned from design documents
and commit messages when used to justify keeping old code paths. Use
"incomplete (deferred to Track N because [reason])" instead. This forces
the deferral to be specific, tracked, and justified — rather than
rationalized.

** Scaffolding-Hides-Truth — Principled Refactor Surfaces Real Facts

When defensive guards, hardcoded constants, or callback parameters are
introduced as scaffolding (often for "safety" or "backward-compat"),
they don't merely add overhead — they actively hide architectural,
algebraic, or structural facts from observation. The system's true
posture is masked because the scaffolding's behavior MIXES with the
underlying mechanism, producing observed results that conflate the two.
The principled refactor that retires the scaffolding doesn't just clean
up — it /surfaces facts the scaffolding was hiding/.

*The pattern* (3 data points across SRE Track 2I, 2026-04-30):

1. *Phase 2a* — ~with-handlers~ silent-skip in the property-sample
   generator (~sre-sample-generator.rkt~). Was scaffolding "for safety"
   against reconstruction failures of compounds with sentinel-component
   inputs. /Hidden truth/: lattice sentinels (bot/top) are NOT valid
   structural components — feeding them through reconstruction produces
   malformed values. The principled fix (per-component-spec pools that
   filter sentinels) revealed the structural distinction between
   "valid lattice elements" and "valid structural components." Without
   the refactor, the scaffolding silently swallowed the malformed
   compounds and made all downstream analysis lattice-incomplete.

2. *Phase 3c* — always-installed ~current-lattice-subtype-fn~ callback
   in the type lattice. Was scaffolding "for principled extensibility"
   added in Track 2H. /Hidden truth/: under PPN 4C T-3 Commit B's
   union-aware merge, the type lattice under equality merge IS
   distributive on hand-picked-6 (216/216 triples). Track 2G had found
   "type lattice not distributive" — correct AT THE TIME, before T-3
   restored distributivity. The callback's mixed semantics (subtype-aware
   meet under all relations) hid that restoration. Phase 3c retired the
   callback for per-relation ~meet-registry~ dispatch, surfacing the
   true post-T-3 algebraic posture.

3. *Phase 4* — hardcoded ~'equality~ constant in
   ~test-distributive~ / ~test-sd-{vee,wedge}/detailed~ for join lookup.
   Was scaffolding from Phase 1+2 era when only equality-relation joins
   existed. /Hidden truth/: per-relation merge-registry has existed

** CALM Requires Fixed Topology — Dynamic Topology Requires Stratification

The CALM theorem (Consistency As Logical Monotonicity) guarantees that
monotone computations over a *fixed* lattice converge to the same
fixpoint regardless of evaluation order. This is the theoretical
foundation for BSP scheduling, parallelism, and order-independent
propagation. The key word is FIXED.

If a propagator's fire function creates new cells or propagators
(dynamic topology), the lattice itself changes during computation.
CALM says nothing about convergence over a changing lattice. In
practice, BSP scheduling silently drops structural changes (new
cells, propagators) because =fire-and-collect-writes= only diffs cell
VALUES. The structural changes exist in the returned network but are
discarded during bulk merge. This produces wrong results — not errors,
not crashes, just silently wrong answers.

*Discovered in*: BSP scheduler vs SRE subtype decomposition.
=sre-decompose-generic= creates sub-cells and sub-propagators inside
fire functions. Under DFS, this works because the full returned
network is used. Under BSP, the structural changes are lost:
=PVec Int <: PVec Nat= returned =true= (should be =false=) because
the decomposition that would detect the violation never materialized.

*The invariant*: Within a stratum, the network topology is FIXED.
Propagator fire functions may only write cell values
(=net-cell-write=). Creating cells (=net-new-cell=) or propagators
(=net-add-propagator=) requires a stratum boundary. *Mechanism (corrected
2026-06-03)*: =current-bsp-fire-round?= is NOT an error gate — it is a
DISPATCH DISCRIMINATOR. Decomposition dispatchers read it and emit a topology
REQUEST when in-fire (decomposing inline only under DFS); =net-add-propagator=
reads it to DEFER worklist scheduling. =net-new-cell= and =net-add-propagator=
are ALLOWED in-fire and CAPTURED (applied by the topology stratum between
rounds) — they do NOT error. (The earlier "guard produces an immediate error"
framing, and the stale code comment at =propagator.rkt:2170-2171=, were
inaccurate; verified during the scheduler O(diff) work — see
=docs/tracking/2026-06-03_SCHEDULER_ODIFF_OPTIMIZATION.md= §7.1.)

*The architectural pattern*: Separate two fixpoints.
1. *Topology fixpoint*: what cells and propagators exist. The set of
   cells/propagators grows monotonically (a lattice under subset
   ordering). Topology changes are processed in a dedicated stratum.
2. *Value fixpoint*: what values cells hold. BSP-safe, parallelizable,
   order-independent. Runs within a stratum over the fixed topology.

The cycle: value stratum (BSP) → topology stratum (sequential:
process decomposition requests, create cells/propagators) → value
stratum (BSP over expanded topology) → repeat until neither changes.

*Implications*:
- *SRE decomposition*: Must emit decomposition REQUESTS as cell
  values, not directly create cells/propagators. A topology stratum
  reads requests and builds structure.
- *Hypergraph rewriting (PPN, PRN)*: Rewrite rules that add nodes or
  edges are topology changes. They must be stratified — rewrite
  application in one stratum, value propagation in the next.
- *Tabling/memoization*: If tabling creates new cells for cached
  results, that's a topology change requiring stratification.
- *Any future construct* that dynamically extends the network: the
  CALM guard will catch it at the API level, preventing silent
  incorrectness.

This is the Correct-by-Construction principle applied to scheduling: the
dispatcher self-gate makes *decomposition* structural (request-emission, not
an inline topology change in-fire). Note (2026-06-03): the flag does NOT
hard-error on a rogue in-fire =net-new-cell=, so the narrower invariant "a
mid-fire-created cell carries no decomp/domain metadata" is convention-
maintained — the scheduler O(diff) work added a debug-mode assert
(=current-check-fire-invariants?=) that makes a violation LOUD, and validated
the invariant holds suite-wide.

See commit =af35f5e= (CALM topology guard implementation).

** Racket Parallelism Has a Hard ~8μs Floor — Measure Before Parallelizing

Racket's cross-thread communication has a measured ~8μs floor (OS
thread wakeup cost). Sync-pool crossover against sequential execution
for ~0.5μs per-propagator work is N≈256. No Racket-level mechanism
beats this floor:

- Spin-wait: workers sleep during merge phase — spin window too short
- Sync events: 15–20μs dispatch per call
- Async-channel: ~30μs per call
- Spin-poll done-semaphores: 2400μs catastrophic busy-spin

*The arithmetic*: parallelism only helps when per-propagator work
exceeds a multiple of the wakeup cost. Below ~16× the floor
(~125μs per propagator), thread overhead dominates — parallelism is
a regression, not a speedup.

*Methodology — measure before parallelizing*:
- Measure actual per-propagator work (μs) at typical workloads
- Benchmark sync-pool vs sequential at multiple N values
- Don't trust design-time crossover estimates — Phase 0c estimated
  thread crossover at N≈128 with 1.9× speedup; actual is N≈256 and
  payoff only at N≥512
- Run 4+ alternative approaches before concluding (spin/sync/async/poll)

*Memory cost is a separate axis, measure it too*: parallel
infrastructure allocates even when unused (worker pool threads,
channels, per-worker state). Racket's GC pauses also affect
cross-thread coordination — a GC in one worker stalls others at
the barrier. Measure allocation rates AND retention, not just
wall-clock:
- Worker pool baseline: memory for K threads + channels (regardless of use)
- Per-dispatch allocation: channel write + thread wake + CHAMP fork
- GC amplification: parallel rounds have K× allocation pressure
  vs sequential for the same work

*Implications*:
- Parallelism in Phase 0 (Racket) pays off only for specific workloads
  (N≥256, per-propagator work ≥ ~5μs)
- True parallelism gains are a compiler/runtime problem, not a
  library problem — self-hosted Prologos with lighter threads shifts
  this boundary
- Parallel infrastructure should be threshold-gated: install the
  infrastructure, but don't use it below measured crossover
- Architecture design should NOT assume free parallelism even if the
  theoretical structure is parallelizable

*Discovered in*: BSP-LE Track 2B Phase 2d (streaming BSP
investigation — 4 approaches benchmarked exhaustively, all worse
than sync pool). Full decomposition in Track 2B PIR §7 (Where We Got
Lucky), §8.1 (surprise), §12.5 (what we learned), §16.6. Strategic
decision: wait for self-hosting. Research note:
=docs/research/2026-03-26_PARALLEL_PROPAGATOR_SCHEDULING.md=.

*Actionable guidance*: for any parallel-targeting design, measure the
work/wakeup ratio and run the 4-approach benchmark suite (sync pool,
spin-wait, sync events, async-channel) before committing. If work
< 16× wakeup floor, design as threshold-gated infrastructure with
sequential default — not as a parallel mechanism with sequential
fallback.

capture-gap discovery mechanism. The capture-gap pattern names
WHAT goes wrong (parallel surfaces missed); audit-first names HOW
to catch it (run grep enumeration before implementation, present
Wide vs Narrow if scope expands).

*Discovered in*: PPN 4C Phase 9+10+11 addendum Step 2 arc
(2026-04-25). User-directed at S2.e-i opening ("audit first, then
review shortly before heading into implementation"); validated

** Audit-Driven Scope Expansion: Wide vs Narrow Decision Point

When pre-implementation audit reveals more surfaces than the design
names, present **Wide vs Narrow** as a decision point to the user.

- *Wide* = comprehensive cleanup atomically (retire all
  audit-discovered surfaces in one sub-phase)
- *Narrow* = retire only design-named surfaces; defer
  audit-discovered surfaces to follow-up sub-phase or future phase

*Pattern observed across 2 data points* (PPN 4C Phase 9+10+11
addendum Step 2 arc, 2026-04-25):

1. *S2.e-iv split (Wide variant)*: design's "deletion" estimate
   became Cat A + Cat B + Cat C sub-phases. User-directed
   "stick to the design; breaking into multiple subphases is fine."
   Wide-by-decomposition: same scope, finer-grained sub-phases.
2. *S2.e-v Wide retirement*: design named 2 functions; audit
   revealed 6. User-directed Wide ("Wide + Migrate, I agree
   with your lean on these"). All 6 retired atomically.

*Decision recommendation*: recommend Wide unless cost prohibitive.
Reasons:
- Capture-gap pattern (above) makes deferred audit-discovered
  surfaces drift-prone — they get missed in subsequent sub-phases
  unless explicitly re-captured.
- Atomic cleanup is more architecturally coherent than serialized
  cleanup across multiple sub-phases.
- The cost difference is usually small — audit-discovered surfaces
  are typically parallel patterns that share retirement mechanics
  with the design-named ones.

*Cost-prohibitive criteria* (when Narrow is appropriate):
- Audit-discovered surfaces require fundamentally different
  mechanism than design-named ones (rare; usually they're parallel)
- Sub-phase scope balloon would push past the 1-hour conversational
  cadence rule (split via S2.e-iv pattern instead)
- User context-window or implementation cost concerns

*Discovered in*: PPN 4C Phase 9+10+11 addendum Step 2 arc
(2026-04-25). 2 data points; codification here so the decision
point is explicit at every audit-driven scope expansion.

*Connection to other patterns*:
- Audit-first (above) is the discovery mechanism
- Capture-gap (above) names the failure mode of Narrow without
  re-capture
- Wide is the principled response that prevents drift

** Mini-Audit Must Verify Carrier Capability AND Check For Existing Helpers

When a mini-design cites a precedent or applies an architectural
pattern (e.g., "Realization B applies here"; "this fits the X
pattern"; "we use existing primitive Y"), the mini-audit must verify
TWO independent questions:

1. *Carrier capability*: does the SPECIFIC cell / structure / module
   in question actually support the architectural pattern being
   applied? (Not "does the precedent demonstrate the pattern works"
   — the local carrier may have a different capability profile.)
2. *Existing helpers*: does the codebase already have a helper /
   primitive that closes the capability gap? (Not "let's design a
   new mechanism for this need" — grep for the helper first.)

Either gap, missed at mini-audit time, costs at least one halted
implementation cycle.

*Pattern observed across 3 data points* (PPN 4C addendum):

1. *S2.c-iii ~with-handlers~ wrapper preservation* (2026-04-24):
   mini-audit catalogued "all 9 dispatch functions converted ✓" but
   didn't check whether the inherited ~with-handlers~ wrapper from
   PM 8F was preventing the option-4 perf claim (~302 ns/call) from
   landing. Architecture's SHAPE preserved without its BENEFIT.
   External user challenge surfaced; Move B+ corrected. See
   ~workflow.md~ "Microbench claim verification" + DESIGN_METHODOLOGY
   adversarial VAG codification.

2. *2A.b handler-as-scaffolding* (2026-05-20): mini-design
   recommended an ad-hoc handler-mechanism extension. Audit didn't
   surface that the deeper concern was the handler-mechanism itself
   (PM Track 13 spin-off territory). User challenge reframed; new PM
   track captured the concern at the right level.

3. *3A.b carrier-capability + missed helper* (2026-05-22): mini-design
   cited "BSP-LE 2/2B Realization B applies" but didn't verify (a)
   whether the SPECIFIC attribute-map carrier supported
   ~tagged-cell-value~, AND (b) whether ~promote-cell-to-tagged~
   (propagator.rkt:1579, used at 5 production sites in relations.rkt)
   existed. Implementation halted at E2E test failure. Audit surfaced
   both gaps; Option E fixed. See PPN 4C Phase 9 design §9.3.4.

*The principle*: a precedent demonstrates a pattern WORKS in some
context. It does NOT demonstrate the pattern APPLIES in the new
context. Mini-audit must independently verify the LOCAL carrier and
LOCAL helpers — even when (especially when) confident the pattern
applies.

*Process discipline*: at mini-audit time, for each cited precedent
or applied pattern, run TWO grep / Read passes:

1. *Carrier verification*: read the SPECIFIC carrier's merge function,
   struct definition, and access API. Verify it supports the pattern's
   capability requirements (e.g., for Realization B: does the carrier
   support tagged-cell-value, or does it need ~promote-cell-to-tagged~
   first?).
2. *Helper enumeration*: grep for primitives / helpers in the
   ballpark of the capability need. Existing helpers usually have
   doc-strings naming the precondition ("Must be called BEFORE
   speculative writes under a non-zero worldview" — propagator.rkt:1581)
   that name the exact gap the mini-audit might miss.

*Why this matters*: the cost of these two greps is ~5 minutes per
audit. The cost of missing them is at least one halted
implementation cycle, one mini-design revision, and one test-run
diagnostic round (typically 1-2 hours of work + context switching).
The asymmetry strongly favors running the checks.

*Adversarial 3-column framing IS necessary but not sufficient* —
all three data points had adversarial framing applied at their
relevant gate, and all three drifted past it. The adversarial column
catches drift WHEN the question is asked; the carrier-capability and
existing-helper questions must be asked EXPLICITLY (catalogue
question 2 in the mini-audit checklist), not left to general
adversarial framing.

*E2E tests are mini-audit power tools*: the 3A.b carrier-capability
gap was caught by an E2E test failure in ~5 minutes. The
grep-based mini-audit missed it. E2E tests that exercise the
specific architectural property (per-branch isolation, tagged-aware
reads, etc.) provide empirical confirmation that mini-audit static
checks cannot.

*Discovered in*: PPN 4C addendum cross-arc (3 data points across
S2.c-iii / 2A.b / 3A.b). User-articulated framing during 3A.b audit
review (2026-05-22): *"Let's audit the code that these decisions
touch on first, to ground our context to the reality of the
codebase."* Graduation threshold met (3 data points + user
direction). Codification here makes the carrier-capability +
existing-helper checks an explicit mini-audit step.

** Sed-Deletion of Parameterize Bindings Is Error-Prone for Last-Binding Lines

When sed-deleting parameterize bindings, MUST use 2-pass pattern:
substitution preserves the closing paren for last-binding-in-block;
deletion removes plain bindings. Single-pass deletion breaks the
parameterize blocks where the deleted line had the closing paren.

*The bug*:

#+begin_src bash
# WRONG — matches both `(make-hasheq)]` (regular) AND
# `(make-hasheq)])` (last-binding-in-parameterize-block).
# For the latter, deletes the closing `)` → unbalanced parameterize.
sed -i '' '/\[X (make-hasheq)\]/d' file.rkt
#+end_src

*The fix (2-pass pattern)*:

#+begin_src bash
sed -i '' \
  -e 's/^\([[:space:]]*\)\[X[[:space:]][[:space:]]*(make-hasheq)\])/\1)/' \
  -e '/\[X[[:space:]][[:space:]]*(make-hasheq)\]/d' \
  file.rkt
#+end_src

The first line (substitution) handles `(make-hasheq)])` — replaces
the entire binding (preserving leading whitespace via captured `\1`)
with just the closing `)`. The second line (deletion) handles
`(make-hasheq)]` (no trailing paren).

*Verification before batch*: test on 1 file via copy to /tmp, run
sed, then ~tools/check-parens.sh~ to verify balance. Don't apply
batch sed to many files without single-file verification.

*Pattern observed in PPN 4C S2.e-iv-c (2026-04-25)*: initial
single-pass sed broke 94 parameterize blocks. Detection only via
FULL SUITE (test-session-runtime-03.rkt read-syntax error;
targeted tests on the metavar-store/universe domains all PASSED
because the broken parameterize blocks were in OTHER test files).
Recovery via ~git checkout HEAD --~ revert + smart 2-pass sed.

*Why this matters*: large-scale test fixture surgery is high-leverage
when pattern uniformity is verified (audit-first), but high-risk
when sed patterns have edge cases. The 2-pass pattern removes the
edge case. Test-mode isolation (1 file via copy + check-parens)
catches the bug before batch.

*Operational rule*:
1. Audit-first to verify 100% pattern uniformity across target files
2. Test sed on 1 file copy in /tmp before batch
3. Use 2-pass pattern (substitution + deletion) for parameterize
   bindings
4. Run check-parens after batch to verify balance
5. Run FULL SUITE as regression gate (NOT just targeted tests —
   the bug may manifest in unrelated test files via cascading
   read-syntax errors)

*Reinforces existing rule*: ~workflow.md~ "full suite as regression
gate when touching code is RULE." This sed-mistake is a strong
data point for that rule — targeted tests on the directly-affected
files all PASSED while the regression was real.

*Discovered in*: PPN 4C Phase 9+10+11 addendum Step 2 S2.e-iv-c
(2026-04-25). 1 high-confidence data point — codifying as
operational rule because the failure mode is structural (parameterize
bindings universally have this shape) and the fix is mechanical
(2-pass pattern).

** Microbench-Claim Verification Pays Off Across Sub-Phase Arcs

When a phase's design references a microbench finding as load-bearing
for a quantitative claim (e.g., "option 4 wins by 302 ns/call"), the
phase's CLOSE must include re-microbench to verify the claim landed
AND maintained through subsequent sub-phases. Architectural-shape
delivery is NOT sufficient — the perf claim must be VERIFIED, not
assumed to have landed AND not assumed to have persisted.

*Pattern observed across 3 data points* (PPN 4C addendum Step 2 arc,
2026-04-24 → 2026-04-25):

1. *S2.c-iii first-pass*: implemented option 4 architectural shape
   but preserved ~with-handlers~ wrapper from PM 8F era (which was
   the SOURCE of the 302 ns/call delta). User external challenge
   ("did we do anything about the cache fields?") surfaced the gap.
   First-pass VAG passed cataloguing without challenging.
2. *S2.c-iii Move B+ corrective (commit ~c86596e0~)*: dropped the
   ~with-handlers~ wrapper + ignored explicit-cid for universe-active
   path. Re-microbench: Path 1 went 625 → 388 ns/call (~80% of
   predicted 302 ns benefit captured).
3. *S2.c-iv close re-microbench*: Move B+ benefit SURVIVED the next
   sub-phase. Path 1 stayed at ~372 ns/call (~84% of predicted
   benefit retained). This confirmed the architectural change held
   through subsequent retirement work.
4. *S2.e-v close re-microbench*: Move B+ benefit MAINTAINED through
   5 subsequent sub-phases (S2.c-iv → S2.d-level → S2.d-session →
   S2.d-followup → S2.e-i → S2.e-ii → S2.e-iii → S2.e-iv-a/b/c → S2.e-v).
   Path 1 at 367-373 ns/call across 3 workloads; Path 4 still
   strictly dominant.

*The principle*: closes the Pre-0 microbench → Stage 4 verification
loop. Per-sub-phase obligation, NOT just track-level post-implementation
activity. When a perf claim is load-bearing for an architectural
decision, verify at EACH subsequent sub-phase that could affect it.

*Operational rule* (codified at ~workflow.md~ "Post-implementation
microbench-claim verification" via commit ~9f7c0b82~): when a phase's
design references a microbench finding as load-bearing, the phase's
CLOSE re-microbenches. This rule pays off; codify the extension that
"verification at EACH subsequent sub-phase that could affect the
perf claim" is the discipline.

*Why this matters*: the alternative (verify once at the implementing
sub-phase, assume held thereafter) would have missed any subsequent
regression. The Move B+ verification across 5 sub-phases gave
confidence the architectural change was DURABLE, not just
momentarily achieved.

*Discovered in*: PPN 4C Phase 9+10+11 addendum Step 2 S2.c-iii Move
B+ corrective (2026-04-24) → S2.c-iv close (2026-04-25) → S2.e-v
close (2026-04-25). 3 data points; codification here extends the
existing rule with the per-sub-phase-arc discipline.

*Catalogue vs Challenge framing*: the catalogue "we shipped the
architecture" is NOT the challenge "did we capture the perf benefit
the architecture was supposed to deliver, AND did we MAINTAIN it
through subsequent sub-phases?" Both Catalogue1 (shipped) and
Catalogue2 (initially captured) miss the Challenge (durably maintained).

** External Cross-Impl Gates Substitute for Self-Validation

When a track ports a protocol against an external counterparty, a
foreign-generated golden + drift gate is a stronger test than any
hand-written assertion. Hand-written tests validate against your
understanding of the spec; foreign-generated tests validate against
the spec itself.

*The pattern*. The OCapN interop track ran ~tools/interop/gen-syrup-vectors.mjs~
inside ~@endo/ocapn~, committed the output as a fixture, and added a
CI step ~git diff --exit-code~ on the fixture. Any change to the JS
encoder forces a fixture update; any drift between Racket encode/decode
and JS encode/decode triggers a test failure on the next CI run.

*Result*. 4 of 5 interop bugs in the OCapN track (UTF-8 byte length,
~null~ as record child, multi-arity record encoding, sign-suffix on
int) were caught by this gate. None would have been found by
hand-written tests because the test author shared the same
misunderstanding as the encoder author.

*The implication for D:I ratio*. The longitudinal target for
design-to-implementation is 1.5:1. OCapN's ratio was ~0.17:1. The
track succeeded because the external spec plus the foreign-generated
drift gate substituted for design rounds. **The D:I target is
conditional on whether external validation exists**: with an external
counterparty + drift gate, low D:I is fine; without one, low D:I is
technical debt.

*Operational rule*. When porting a protocol or implementing against
an external spec, a foreign-generated drift gate is **mandatory test
infrastructure**, not optional. Add it as Phase 1 work, before the
encoder/decoder code. Treat hand-written wire vectors as a last-resort
substitute for foreign goldens.

*Discovered in*: OCapN Interop track (2026-04-29 → 2026-05-04, PIR
2026-05-04). 1 data point as a track-defining lesson; codified
proactively because the pattern generalizes to any future protocol
port (XMPP, Matrix, MLS, etc.).

** Closed-World ~data~ Is a Phase-0 Simplification, Not a Permanent Architecture

When porting against a language with first-class user-extensible
behaviors (Goblins's runtime-defined actor closures, Erlang's
dynamic ~gen_server~ callbacks, etc.), and the target language
(Prologos) has only closed-world ~data~ declarations, the
right Phase-0 move is to **enumerate the behaviors needed for
acceptance** and call it scaffolding with a retirement plan. The
wrong move is to insist on first-class behaviors before any wire
bytes flow.

*The pattern*. OCapN Phase 0 enumerated 7 behaviors (cell, counter,
greeter, echo, adder, forwarder, fulfiller) as a closed ~BehaviorTag~
~data~ declaration. 117 tests green in one session. Phase 22
(open-world behaviors) DEFERRED with explicit language-blocker
rationale: needs heterogeneous existential containers OR first-class
trait-method values, neither of which exist in Prologos today.

*Why this works*. Phase-0 acceptance does NOT need user-extensible
behaviors; it needs a vat algebra that proves the wire algebra. The
language gap becomes visible to the next phase, when behaviors need
to come from outside the prelude.

*Operational rule*. When a port faces a language gap, take the simpler
version with a clear retirement plan. Name it as scaffolding in the
design doc, schedule the retirement phase, do not let the language
gap block the port. Forbidden phrasing: "we'll come back to it."
Required phrasing: "DEFERRED to language phase X because Prologos
lacks Y, retirement criterion is Z."

*Discovered in*: OCapN Interop track Phase 0 + Phase 22 deferral
(2026-04-27 → 2026-05-04). 1 data point but generalizes to any
application port hitting a language gap.

** Helper Chains Around Nested-Match Elaboration

Three-deep nested ~match~ inside a single function body fails to
elaborate at *import time* with "Unbound variable" errors in
Prologos's current elaborator. The fix is mechanical: factor into
a chain of single-match helpers. This shipped twice in the OCapN
track (Phases 15 and 21) before the pattern was codified.

*The pattern*. Replace ~defn f [x] match a | ... | _ -> match b | ... | _ -> match c | ...~
with three helpers: ~f~ matches ~a~ and dispatches to ~f-step2~
which matches ~b~ and dispatches to ~f-step3~ which matches ~c~.
Same semantics for the user, no elaborator failure.

*Why this matters*. Until the underlying elaborator bug is fixed,
this is the safe pattern. Each occurrence cost ~30 minutes of
diagnosis on a failing import. Recognizing the shape on sight is
worth it.

*Operational rule*. Never write three-deep nested ~match~ as a single
function body. Always factor into a chain. Codified in
~prologos-syntax.md~.

*Discovered in*: OCapN Interop track Phase 15 (commit ~594ce90~,
question-table mapping) and Phase 21 (commit ~c8782e9~, pipelining
helpers). Two occurrences within a single track was the threshold
for codifying as a workaround.
** Cell / Propagator / Scheduler Orthogonality — Codified Architectural Principle

When optimization pressure surfaces on the propagator substrate, the natural
temptation is to reach for whatever's easy to implement in the current
scheduler. The hybrid pivot's "Option E (BSP-aware piggyback)" was an
example: piggyback the threshold check into BSP's worklist drain pass.
Easy to implement; wrong layer.

*The principle* (codified in [[file:DESIGN_PRINCIPLES.org][DESIGN_PRINCIPLES.org § Cell / Propagator /
Scheduler Orthogonality]]): the architecture has three orthogonal layers
(Cell, Propagator, Scheduler), and optimizations should be located at the
layer that owns the concern. Mixing layers breaks scheduler-portability
(violates CALM's order-independence in practice) and creates re-implementation
debt for every new scheduler.

*The discipline*: when an optimization is tempting because "it's easy to
implement in scheduler X," that's a red flag. The optimization is at the
wrong layer. Find the equivalent optimization at the cell or propagator
level — even if it's harder to implement initially, it preserves portability
across all current and future schedulers (Gauss-Seidel, BSP, Zig-LLVM,
self-hosted runtime, future distributed runtime).

*Origin*: PPN 4C tropical addendum D.3.EC critique review (2026-05-14). The
user articulated the orthogonality principle in response to the hybrid pivot
exploration. The principle rejected "Option E (BSP-aware piggyback)" and
motivated a redesign of Phase 1B/1C toward on-network optimized cell type
(storage strategy + fire-on policy at cell + propagator level).

*Application going forward* (prophylactic discipline):
- *PReduce series*: e-graph cost extraction inherits the cell-level
  monotone-counter optimization pattern; no scheduler coupling
- *OE Series*: cost-bounded exploration uses cell-level specialized storage;
  no BSP-specific piggybacking
- *SH Series*: self-hosted scheduler runs existing networks unchanged
- *Future tracks*: every optimization decision passes the "does this couple
  to scheduler-specific behavior?" test BEFORE implementation

*Anti-pattern catch* (apply at design and implementation time):
- "This is easy to add to BSP's worklist drain" → red flag; move to cell/prop layer
- "This cell behaves differently under sequential vs parallel" → CALM violation
- "Porting to scheduler X requires re-implementing this optimization" → wrong layer
- "The scheduler needs to know about this special cell type" → cell-mech should be opaque to scheduler

Codified 2026-05-14 from a single user-articulated insight during external
critique resolution. Treated as foundational architectural principle (added
to DESIGN_PRINCIPLES.org as a top-level principle, not just a watching-list
candidate) because the alternative — hybrid pivot scaffolding propagating
across PReduce/OE/SH Series — would have created compounding architectural
debt across multiple multi-month tracks. The cost of codifying now is one
session; the cost of re-deriving for each track is multi-session × N tracks.

** Cache Projection Should Model Read-Side + Write-Side Independently

When projecting performance savings from caching a hot cell or struct
field, model BOTH read-side AND write-side savings independently based
on actual access patterns. Don't project one side and assume the other
contributes similarly — they're often asymmetric, especially under
deferred-write architectures where reads dominate the hot path.

*The trap*: a projection anchored only on write-side cost (e.g., "we
save X ns/call on cell-write") undermodels the win when the cell is
read-heavy on a hot loop. PPN 4C 1V-3 Item #1-bis projected ~0.3 ns/cycle
savings (write-side only); actual savings were ~1.82 ns/cycle (~6×).
The unmodeled side: the BSP convergence check at `propagator.rkt:2670`
fires `(net-cell-read net fuel-cell-id)` every iteration. Auxiliary
per-call metrics confirmed it: cell-read -85% (74 → 11 ns/call);
check-site -86% (77 → 11 ns/call) — neither was in the projection.

*The discipline*:
1. /Enumerate access patterns separately/: how many reads vs writes per
   representative cycle, and where do they fire on the hot path?
2. /Project read-side savings/ based on read-call cost reduction
   (e.g., champ-lookup elimination → ~20-40 ns/call savings × per-cycle
   read frequency)
3. /Project write-side savings/ based on write-call cost reduction
   (rarer under Option-13-style deferred-write architectures)
4. /Sum independently, don't average/ — read-heavy and write-heavy cases
   amortize differently at different N
5. /Verify with auxiliary per-call measurements/ alongside amortized
   cycle cost — the amortized number can DILUTE per-primitive savings

*Symptom of the trap*: when actual savings exceed projection by >2×,
suspect the projection over-weighted one side. Under-projecting opens
the door to "the gate is unreachable; let's relax it" arguments;
Item #1-bis would have appeared insufficient under the ~0.3 ns/cycle
projection but is comfortably gate-passing under corrected modeling.
Honest projections preserve the gate's correctness signal.

*Codification status*: 1 data point (PPN 4C Item #1-bis, 2026-05-17).
Strong methodological case — the 6× discrepancy is concrete and
traceable to the specific unmodeled read-side savings.

  Across Sub-Phase Arcs" — companion discipline (re-microbench validates

** Cache Write-Through With Persistent CHAMP: Explicit Audit List IS the Drift Mitigation

When adding a struct-field cache that mirrors a persistent CHAMP entry,
the audit must enumerate ALL mutation sites that update that entry. The
enumeration list (WT-1, WT-2, ..., WT-N) IS the implementation checklist
AND the drift mitigation — there's no separate test that catches a
missed site; the enumeration discipline IS the test.

*The trap*: persistent CHAMP semantics mean writes return a NEW network
with a NEW cells map. A cached prop-cell reference goes STALE the moment
any code path updates the entry without also updating the cache. The
cache invalidation problem is structural; consistency requires
write-through at EVERY mutation site.

*Pattern* (PPN 4C 1V-3 Item #1-bis, 2026-05-17): the fuel-cell-cache on
prop-net-warm required write-through at 8 explicit sites + 2 inherited
via delegation. Explicit: WT-1a/1b (net-cell-write fast-path 2 branches),
WT-2 (net-cell-write/slow-path), WT-3 (net-cell-reset), WT-4 (net-cell-
write-widen defensive), WT-6a/6b (net-clear-dependents + net-remove-
propagator-from-dependents), WT-8 (net-cell-replace defensive).
Inherited: WT-5 (promote-cell-to-tagged → WT-3), WT-7 (fork-prop-network
→ WT-3 ×2). Sister precedent: 1B-ii `under-speculation?` cache (simpler
case; only one WRITE site at BSP fire-and-collect-writes refresh).

*The discipline*:
1. /Enumerate all code paths that mutate the cached entry/ — grep for
   `struct-copy <containing-struct>` + the `(<cell-struct> ...)`
   constructor sites + indirect mutation via delegation
2. /Classify each site as EXPLICIT or INHERITED/ — explicit sites need
   inline cache update; inherited sites flow through delegation naturally
3. /Add the conditional update inline at each EXPLICIT site/ — pattern:
   `[<cache-field> (if (eq? cid <well-known-id>) new-cell (<accessor> <warm>))]`
4. /Verify with cache consistency tests/ — read after each mutation kind
   (write/reset/fork/promote/dependents-change) returns expected value;
   cache identity matches champ-lookup result for the well-known id

*Why explicit enumeration*: persistent CHAMP write-through is not type-
checked. A missed site produces silent cache inconsistency (cached value
doesn't match cells-map source-of-truth). The audit list IS the
implementation checklist — there's no compiler help here. Pre-implementation
enumeration is also the drift mitigation against future code paths that
add new mutation sites without updating the cache; those future paths
will appear in the next sub-phase's audit as a new WT-N site.

*Codification status*: 1 data point with concrete enumeration discipline.
Reusable for any future struct-field cache mirroring CHAMP entries —
PReduce e-class cell-cache, PM 12 module-registry-cache, etc.

  with audit findings (WT-1 through WT-8 + inherited)

** "Spike Validates Feasibility, Not Optimality" — Distinguish Acceptable from Best

When a Pre-0 spike PASSES its decision criteria, the verdict is "the
architecture is FEASIBLE at acceptable cost" — NOT "the architecture is
OPTIMAL." A passing spike doesn't foreclose better alternatives; it only
forecloses worse-than-target alternatives. Stage 3 should continue surfacing
refinements even after the spike PASSES.

*Pattern* (1 data point, PPN 4C tropical addendum 2026-05-15): the §13.6
spike PASSED with W1+ = 6.4 ns/call (≤ 30 ns target, ~4× under). The verdict
was "D.4 canonical." During Phase 1B mini-design, a friend's question about
fuel-cell write semantics surfaced an architectural lever (Option 13
deferred-write at round boundaries) that the spike hadn't tested. Option 13
estimates ~2 ns/cycle amortized — ~3× better than the spike's 6.4 ns. The
spike validated D.4 (Option Y per-fire) as feasible; it did NOT validate
that Option Y was optimal vs Option 13 deferred-write.

*The lesson*: a passing Pre-0 spike doesn't close design exploration. It
narrows the field to "architectures that pass the spike's criteria"; further
refinement may surface better-performing architectures within that field.
Stage 3 critique rounds should continue past the spike's PASS verdict.

*The discipline*:
- Don't treat a spike PASS as "design closed"
- Continue surfacing refinements + alternative-within-architecture during
  Stage 3 + Phase mini-design
- Friend-/external-question/-driven exploration is especially valuable
  AFTER a spike PASS (the spike's data informs the exploration; the
  question's outside-perspective surfaces what the spike's framing missed)

*The complementary pattern* (per-phase measurement gates): each
sub-phase boundary in Stage 4 should explicitly measure the design's
performance assumptions and compare against ALTERNATIVES (A/B/C structure).
The §13.7 Per-Phase Measurement Plan codifies this for PPN 4C tropical
addendum. The pattern: design assumptions about performance need explicit
gates that catch divergences early.

** Per-Phase Measurement Plan with A/B/C Structure

When a design's correctness rests on assumptions about performance (e.g.,
"Option 13 achieves ~2 ns/cycle amortized"), the implementation plan should
EXPLICITLY name the measurements that validate each assumption at each
sub-phase boundary. This is stronger than the existing "per-phase
microbench" discipline (`workflow.md` "Benchmark after infrastructure
phases") because it names CONCRETE comparisons (A/B/C variants) and
DECISION RULES (PASS/FAIL/INVESTIGATE), rather than ad-hoc per-phase
measurements.

*Pattern* (1 data point, PPN 4C tropical addendum 2026-05-15): the §13.7
Per-Phase Measurement Plan establishes A/B/C variants for the fuel-cost
write pattern (A = current struct-copy / B = D.4 per-fire / C = Option 13
deferred-write); each Phase 1B + 1C sub-phase has a microbench gate that
validates the C variant against B (post-Phase-1B reference) and A (current
baseline). Measurement work is ~30-60 min per sub-phase × ~6 sub-phases =
~3-6 hours total — but catches regressions when they're cheap to address.

*The principle*: design assumptions about performance need EXPLICIT
measurement gates, not ad-hoc validation. The gate's structure:

- *What's measured* (specific microbench + name)
- *When* (which sub-phase boundary)
- *Against what target* (PASS criterion; numeric)
- *Decision rule* (PASS → continue; FAIL → stop + investigate;
  INVESTIGATE → resolve before next sub-phase)
- *Comparison structure* (A/B/C variants when multiple alternatives are
  in scope)

*Why A/B/C rather than just A/B*: when refinements emerge during Stage 4
(e.g., Option 13 surfaced post-spike), three-variant comparison (current
baseline + spike-validated alternative + production refinement) shows
where the savings come from. With only A/B, the source of the perf delta
is ambiguous; with A/B/C, each delta is attributable.

*The complementary pattern*: see "Spike Validates Feasibility, Not
Optimality" above — the per-phase measurement plan is the discipline that
catches alternatives that improve on the spike's verdict.

Origin: PPN 4C Tropical Addendum Phase 1B mini-design 2026-05-15. The

appropriate places throughout the design to validate our assumptions...
A/B/C test various approaches/assumptions." Watching list: 1 data point;
~1-2 more for graduation.

** Empirical Falsification as Audit Complement

When a mini-audit's reasoning meets a pre-implementation architectural
decision, run a falsification test (probe / microbench / A/B comparison)
with pre-committed criteria BEFORE locking the choice. Audit reasoning is
inference under uncertainty; empirical tests are evidence. The pairing
catches what either alone misses.

How to apply:
- Identify the load-bearing assumption in the audit
- Design the smallest test that would refute it
- Pre-commit interpretation rules (what counts as confirm/refute/inconclusive)
- Run; document the result honestly (negative results are findings, not failures)

** Audit-Precedes-Implementation REFRAMING Discipline

When a mini-audit surfaces a fact the mini-design didn't anticipate,
REFRAME the design before implementing — don't power through with the
original plan plus a footnote. The audit's job is to RESHAPE scope, not
just confirm it.

How to apply:
- When audit reveals an unanticipated finding, STOP implementation
- Decide: reframe (modify design intent), defer (out of scope with capture),
  or override (with explicit rationale persisted in design doc)
- Persist the reframe in the design doc; never bury in commit message alone
- Re-run mini-design dialogue if scope shifts non-trivially

** Dynamic Workflow Is the Generalization of Audit-Delegation — Amplifier, Not Replacement

The =Workflow= tool (deterministic multi-phase multi-agent
orchestration) is the generalization of the already-promoted
audit-delegation pattern: it adds multi-phase orchestration (audit →
design → critique → respond), structured-output schemas, and an
adversarial critique panel as a first-class phase. It is a
*critique-and-audit AMPLIFIER, not a design-and-implement replacement.*

*The core positive (1 strong data point)*: an adversarial
completeness-critic agent caught a LOAD-BEARING flaw in the workflow
/author's own/ design — the workflow's dry-run instruction said "drop
just Layer-2," which leaves the copy loops live and so cannot ATTRIBUTE
residuals=0 to the new write (a recurrence of the §18.18.6.9
misdiagnosis). The author's blind spot was surfaced by the independent
adversarial layer. This is the central argument for the pattern: running
critique lenses BLIND and in parallel /enforces/ the independence that
solo sequential critique erodes by anchoring (lens 4 reads like lens 1).

*The cautions*:
1. *Worktree-HEAD provisioning defect* (2nd data point — see also
   §18.18.6.10): =isolation: 'worktree'= agents have twice been
   provisioned at a STALE base (~26-36 commits behind), SILENTLY — masked
   because absolute-path reader agents in the same run resolve to the
   main checkout at HEAD. Delegated empirical work MUST verify its HEAD
   SHA. Prefer diff-back (workflow returns a patch; main session lands it
   at the known-good HEAD).
2. *Disproportionality*: ~1.96M tokens / 12 agents for a ~4-line change —
   Tier-2 spend on Tier-0/1 work. The critique found real things, but a
   ~2-audit + 3-lens panel would have caught the same load-bearing
   findings at ~1/3 the cost. Start lean; escalate by stakes/breadth.
3. *Co-design tension*: the workflow autonomously front-ran the
   mini-design that is normally co-designed with the user; the user
   reviewed at the END. Acceptable for a LOCKED-approach step (grounding
   + hardening a settled decision); for OPEN architectural questions the
   workflow must STOP at options+critiques and return them, not
   self-resolve.

*The rule*: delegate the "multiple independent minds" work (audits,
critique rounds, mechanical migrations, research sweeps); keep the "one
shared evolving understanding" work (mini-design dialogue, novel
implementation, decision-locking) conversational. The workflow produces
material for a decision; the human + main session makes the decision and
lands the code.

experiment (2026-05-30, §18.18.6.13). See DESIGN_METHODOLOGY.org §
