### LET residual 1 — the fn bracket that swallows a `let` now says so (`226452ae`)

- **Why**: the residual's complaint was about the MESSAGE, and the filing said the fix "wants fn-side layout work". True of making the form work; not true of the message. `[fn [n : Int] let k := 4 …]` reported "parameters must be bare symbols", which points at `n`, which is fine.
- **Surprise**: two silent traps in a four-line predicate. `expand-let` runs over the fn's argument list BEFORE the parser sees it, so `params` holds a `($let-error msg)` marker, not the symbol `let`. And `stx->datum` is SHALLOW, so the marker's head is still a syntax object. Neither errors — the hint just fails to fire and the generic message comes out unchanged, which is indistinguishable from an edit that did not take. Cost two rebuild-and-probe cycles.
- **Fix**: match the marker, unwrap its head. Three pins — the message fires, the workaround it names actually runs, and `[fn 5 …]` still gets the generic message.
- **Residual 2 re-probed and left deferred, but now with a reason**: `classify-let-block` bails at `(< (length cont-elems) 2)` and the reader groups the deeper line into ONE element, so the forgot-body arm is unreachable for the 2-line shape.
