### …and fixed it (`72ce62c9`)

- I filed the `.pnet` dependency-staleness defect as a build-policy call and then reconsidered: option 1 is not a NEW policy, it is the `driver_rkt.zo` check applied to the second input class. A `.pnet` is a function of the Racket compiler AND of every `.prologos` that fed it; the zo check answers the first half, `lib-sources-stale?` now answers the second. Deferring that to an owner was over-caution.
- **Cost measured, not asserted**: ~60 ms scan once per process (memoized), paid only when a lib source is actually edited. Suite 542/10472 at 212 s, inside the variance band, and a warm run still says "55 prelude module caches ready" — the cache is still HIT. That last check is the one a careless fix fails.
- **Trap 1 — the memo must be KEYED BY LIB PATHS.** `current-lib-paths` varies within a process; every test that builds a temp lib rebinds it. My unkeyed box answered for the wrong directory set and turned `test-pnet-registry-restore`'s intended cache HITS into misses — failing two assertions written precisely to catch "a MISS produces the correct answer and proves nothing". Someone else's carefully-worded test caught my bug.
- **Trap 2 — the test needs THREE phases.** "Edit → new answer" also passes if the cache never hits at all, which is the easiest way to "fix" this and the worst. And the MODULE REGISTRY must reset per run: a registered module is never re-loaded from disk, so a shared registry makes phase 3 echo phase 1 regardless of the cache — that cost me a confused half-hour when a fresh-process probe said 110 and the in-process test said 11.
