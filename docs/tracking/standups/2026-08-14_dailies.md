### (ii) EHP P5 ✅ — the `#match?` gate, and the guard it gates was itself silently broken · `9595e514`

**Why**: §3.5 offered lint-or-retire. The relay note sharpened it — all three
uses are plain `^(a|b|c)$`, already translatable — so: *is a lint guarding a
hazard the grammar-token route would delete outright?*

**⭐ ANSWERED NO, and for two of the three the grammar route would be WRONG.**
The predicates match `(identifier)` **by name**, and `@type.builtin` /
`@constant.builtin` are **library names, not syntax** — `Option` is literally
`data Option {A}` in `book/pairs-and-options.prologos:88`. The grammar has no
business knowing them, users may shadow them, and tokenizing them would make the
grammar assert something false. The query's **own comment already draws that
line**. Only the pseudo-keyword list is a candidate → **DEFERRED 137**, filed
OPEN (register 137 → 138). So `#match?` stays regardless, and the lint is not
guarding an absent hazard.

**⭐⭐ THE SURPRISE: the guard was ALREADY BROKEN, and against its own written
contract.** `prologos-ts--translate-regexp` says it raises on anything
untranslatable "so an untranslatable pattern is SKIPPED VISIBLY rather than
shipped dead". Measured: `\d` raises as documented — but **`[\d]` translated
silently**, and means a digit in PCRE versus "backslash or d" in Emacs. The
`\d`-family check fired only **outside** a character class. A silent divergence,
in the one function whose entire job is preventing silent divergence. This is the
**fail-open** shape again — 7 of N now — and the reason it was found is clause 5
of the instrument rule: *check an artifact's CONTRACT before reusing it.* I was
going to reuse the translator as the lint's authority, read its contract to be
sure it was safe to delegate to, and the contract turned out to be false.

**Design note worth keeping**: the gate carries **no notion of its own** about
what is translatable — it calls the translator. Two parallel definitions of one
subset drift, and this project has paid for that shape more than once
(`split-star-lexeme` vs the family table being the live example).

**Fail-proof**: poisoned the query with `^[\d]+$` → exit **1**, pattern named;
restored byte-identical → exit **0**. ⚠ First attempt reported `EXIT=0` because I
had read `tail`'s status, not the gate's — re-checked properly. Extractor tested
against the comment-prose trap this project has hit twice: `#match?` in a comment
→ 0 extractions; comment-then-real → 1; a regex containing `;` not truncated;
escaped `\"` handled.

### (vi) THE KEYWORD-LITERAL STRING CHROME — a THIRD ungated artifact, and Emacs was right because it has no build step · `739ba5fa`

**Why**: owner reported map/keyword-literal chrome matching **strings** in VS
Code while Emacs showed them distinct — an aesthetic regression from TextMate,
and a cross-editor discrepancy.

**⭐ THE CAUSE: `out/` is a third artifact with neither a builder nor a
consumer.** VS Code runs `out/*.js`, not `src/*.ts`. `install.sh` built the
dylib, built the wasm, copied `highlights.scm`, stamped provenance for all of it
— and never compiled the extension. No gate loaded `out/` either, because
`dump-captures.mjs` reads the repo query and the wasm **directly**. So the one
artifact that decides **appearance** was invisible to everything.

Measured: `src/semanticTokens.ts` Aug 15 02:02 versus `out/semanticTokens.js`
Aug **14** 05:29, and the compiled map had **no `string.special.symbol` entry**.
Without it the capture falls down its own dotted root —
`string.special.symbol → string.special → string` — which is precisely the
fallback the source comment says the explicit entry exists to prevent.

**⭐⭐ EMACS WAS CORRECT BECAUSE IT HAS NO BUILD STEP.** It loads `.el` source.
That asymmetry is what disguised a stale build as a cross-editor disagreement,
and it is worth remembering as a diagnostic: *when one editor is right and the
other is wrong, ask which one runs a build artifact before comparing configs.*

**What I ruled out first, by measurement**: both mappings send the capture to the
CONSTANT family · TextMate has exactly ONE string rule (`string.quoted.double`,
matching a quote) so it cannot paint a keyword literal as a string · and in
**Solarized Dark** (read from the owner's settings) string is `#2AA198`,
`constant.language` `#B58900`, `constant.other` `#CB4B16` — all distinct.
Nothing in the configured paths produces string chrome. **That is what pointed
at the build**: the symptom was unreachable from the source, so the source was
not what was running.

**Fixed at both halves**, mirroring the wasm: `install.sh` compiles and stamps
`out/.provenance`; `check-parity.sh` refuses a stale `out/` by content hash,
exit 3, naming both hashes. *A correct builder does not help when nobody runs
it* — the query-sync guard's own comment, one artifact along. The PASS line now

**Also removed a vestigial allowance**: `textmate-agreement.tsv` permitted
`string.special.symbol` to agree with a `string` scope. TextMate can never emit
one there, so it licensed a disagreement that cannot occur — and contradicted the
file's own rule that a real disagreement is two specific scopes that cannot both
