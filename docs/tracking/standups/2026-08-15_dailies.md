### (i) THE CARRIER RULED, AND FOUR MEASUREMENTS THAT EACH CORRECTED THE ONE BEFORE · `3350260c` · `34367df5` · `3b4972c0` · `17571300` · `fff2d09d` · `1241710e` · `d4c85f3c`

**Why**: the owner reframed SURF T1 — take the design deeper per DESIGN/CRITIQUE
methodology, study gopcaml properly, and **reconsider tree-sitter as the
carrier**. gopcaml turned out not to use tree-sitter at all (it links
`compiler-libs`), which converges with our own ambient rule that the compiler is
the authority. **R4 ruled: the HYBRID** — layout carries the always-on
breadcrumb, the compiler tree carries the session.

**Owner correction that changed what we build**: I listed "not incremental" as a
cost of the compiler carrier. It is a fact about **today** — incremental
compilation is the project goal via the propagator network and cell persistence,
and the groundwork is visible (the parse IS the cell pipeline;
`driver.rkt:2564` records the per-form cells as *"cells landed, propagator
wiring unbuilt"*). Consequences: tree-sitter's incrementality edge **expires**,
we must **not** build a stale-tree layer, and the protocol must ask for *the
tree* rather than encode "full reparse".

**Phases resequenced** (owner): breadcrumb first, P3 of 6 → P1–P2 of 9. It has no
LSP dependency, it is the only always-on surface, and the spike now runs
**before** we build an endpoint it could disqualify.

**⭐ P1 — 6769 positions measured. 41% have NO ancestors.** Ancestors-only would
leave the header blank two-fifths of the time, which settles a question taste
would have got wrong. Segment median 20 chars, p90 45; a ~24-char cap suffices;
depth ≥4 is 3% so middle-elision is rare. Real paths like
`def app-config › :server › :ssl` navigate a **data structure** — a node-type
breadcrumb renders that as `map › entry › map › entry`, i.e. nothing. One rule
covers code and data.

**⭐ P3 — the spike, and FOUR wrong measurements before the right one.** Final
answer: the merged tree is **6448 nodes, depth ≤13, ~100% of real source nodes
located, 3 error nodes**. Getting there: (1) my walker counted `srcloc` structs
as tree nodes; (2) it recursed into them, making nothing look degenerate; (3) it
knew only the struct form of the location, reporting **35% coverage** — I was
drafting that as a blocker; (4) I measured the **tree spine**, not production.
The fix each time was to print an actual value rather than reason about the
aggregate.

**⛔ The extractor change we agreed to make must NOT be made.** In the merged
tree there are **zero** list-form locations — the list form is a tree-spine
artifact and the spine is deliberately off (`2026-08-02_LOC_TO_LINE_MERGE_DEFECT.md`
§0: *"the spine must stay off"*). It would be dead code AND would reopen the
0-based/1-based hazard that note closed; its own §0 opens by saying its proposed
"minimal fix" *would have shipped a silent wrong-answer bug*.

**The 8% unlocated is ONE struct**: `binder-info` (520 of 523), which is
`(name mult type)` — no location field, by design, because the binder it
describes carries the position. `io.prologos` yielding **zero** surfs is also
correct: `ns` + 8 `foreign` decls + comments, all preparse-consumed. ⚠ But that
is an API constraint for P4 — the endpoint must distinguish *"parsed fine, no
navigable forms"* from *"failed to parse"*.

**⭐ P4 — session entry is ~9 ms typical, ~138 ms worst.** Payload 6.4–58 KB,
serialize 0.6–4.4 ms, round trip 0.6 ms. ⚠ **My "about 12 ms" in the carrier

`ws-string->surfs` and the cell parse is **10%** of it. So **PARSE T1 fixed the
smaller half**; preparse+merge is the other 90% and is superlinear at ~n^1.6.
