### Stage 3 — the scope, and three corrections to it · `3735332f`

**Why**: `defn centigrade->fahrenheit [c:Posit32] : Posit32` fails with
`defn: expected ':', got >`. Owner reported it as new and caused by recent main
activity.

**It is not new — and the inversion is the finding.** Bisected 661 commits
(automated, one compile per step): first "bad" commit `2a7cbe45` (2026-07-02,
*loud error surfacing*). That commit did not break arrow names; it stopped the
driver **silently discarding** the parse error. Measured at `d8485097`
(2026-06-01): `defn c->f …` alone reported **0 errors while defining nothing**,
and only failed downstream with `Unbound variable`; the control `defn cToF …`
defined and evaluated. So the prior behaviour was a clean bill of health for a
file whose function did not exist. Documented in-tree since 2026-03-18
(`examples/2026-03-18-track7-acceptance.prologos:887-891`).

**Mechanism** (measured, not inferred): a mis-lex. `recognize-symbol` eats `c`,
eats `-` (which **is** in `ident-continue?`), halts at `>` (which is not). The
tokenizer is priority-order first-match-wins, **positional, no backtracking**, so
`recognize-arrow` — anchored on `-` *at the scan position* — never fires, because
that `-` is already consumed. `"c->f"` → `symbol "c-"` · `rangle ">"` ·
`symbol "f"`. The stray `rangle` is **not inert**: it pops a bracket frame, so
`[int->str x]` loses its `[` frame and errors can surface far from the cause.

**Three corrections the audit forced**, each re-verified by hand:
(1) **The rule was mis-stated.** "No surrounding whitespace" would have
mis-described **275 live sites** in lib+examples — the prefix arrow-type form
glues `->` to an opening bracket (`[-> [List A] [Option A]]`; 208 `[->`, 67
`(->`). The rule is **ident-char on BOTH sides**.
(2) **The cited precedent does not exist as framed** (see Watching 2).
(3) **P0 was already done** — the `inject-spec-into-defn` whole-file abort found
while probing is real on the stale branch but already fixed on main by
`ae26f5403`. `7d8520a0b` had separately promoted the governing lesson *"a raise
on the parse path is a WHOLE-FILE abort"* on 2026-08-03.

**Coherence is measured, and it is clean**: 6,051 `->` in the corpus, 5,547 fully
spaced, **0 right-glued in code**; all 13 left-glued sit inside `foreign` string
literals, which `recognize-string` never re-tokenizes. Glued `->` already fails
everywhere today (`spec A->B`, `| p->b`, `<Int->Bool>`), so the rule regresses
nothing. ⚠ But `>` must **never** be added to `ident-continue?`: 1,416 of 1,444
ident-glued `>` chars close an angle group.

**Surprise**: `<` DISCLOSES — which I expected to constrain this — **does not
exist in code**. One comment; D4 schedules it in P4e (⬜).

**Next**: P1.

### P1+P2 — the rule lands, and the arm beats the recognizer · `5616e3c7`

**Why**: `defn centigrade->fahrenheit [c:Posit32] : Posit32` failed. Now works
(100 °C → 212.0).

**The design left the implementation open and the answer flipped.** I had
proposed a new recognizer above `symbol` (50), on the `narrow-var-annot` (96)
precedent. Two loop arms won instead — because the closest precedent is in the
SAME function: `recognize-symbol`'s `::` module-path continuation is already a
fixed two-char lookahead in its scan loop, and `a->b` is exactly that shape, a
continuation WITHIN an identifier rather than a new token kind.
`narrow-var-annot` needed its own recognizer only because `?x:Nat` is a
different token shape.

**Placement is the whole trick**: the arm must precede the `ident-continue?`
arm, because `-` is itself an ident-continue char and would otherwise be eaten,
leaving `>` to end the token — that IS the truncation.

**Surprise (in our favour)**: glued-ness needed **no adjacency substrate**. The
scanner is mid-token, so whitespace cannot occur there by construction. The
scoping had assumed the fused-`:` machinery would be needed; it is not.

**P2 shipped in the same commit deliberately** — a one-commit window where
`recognize-keyword` lagged `recognize-symbol` would BE the F1b.7g drift that
function's own comment records.

**Gates**: corpus A/B via `reader-corpus-ab.rkt`, both legs on ONE pinned
161-file snapshot — **zero diffs**, 0 read-errors per leg. Token battery pins
that angle groups still close (`<Int->Bool>` keeps its `rangle`), the 275
`[-> …]` prefix sites are untouched, and `a>b` is unchanged.

**Next**: P1b.
