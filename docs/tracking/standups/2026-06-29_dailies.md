## The arc (chronological, with the *why*)

### 1. Opening + grounding (4 parallel read-only agents)

Owner wants demos that exercise Process + Relational together: read CSV + a JSON
array of records (Process/IO), schema-validate them (`schema`), and query them
relationally with reusable subqueries over a graph; plus showcase *session-type
composition* (a session type in another's continuation). SQLite deferred until
sub-process infra + a deeper relational fact representation exist.

Rather than design from memory, grounded the *actual* state via 4 HEAD-pinned
agents (Process/IO, `schema`, Relational, session types). Headline:
- **The 3-paradigm table** (`RELATIONAL_LANGUAGE_VISION.org:13`) is the organizing
  insight: `schema` is the **relational "spec"** (the signature that types a
  relation's columns), and `session`/`defproc`/`proc` are the Process column. So
  the demo is "exercise all three columns at once," with `schema` as the
  *connective tissue* (it types both the records and the relations).
- CSV module exists (FFI to `io-ffi.rkt`); **no user-facing JSON parser**; IO is
  thin; the relational engine (`defr`/`solve`/recursion/joins) is solid; session
  basics run at L3, composition is partial.

### 2. Stage-3 design — D.1 → D.2

Wrote D.1 (the dependency-resolver demo concept), captured owner decisions
(D1–D7), then ran an **independent P/R/M/S critique cycle** (4 adversarial
reviewers). The critique earned its keep — it caught **two blocking defects
before any implementation**:
- **`Result` short-circuits** (S-lens): stdlib `Result.map2` stops at the first
  error; validation that should accumulate ALL field errors needs a `Validation`
  applicative (Semigroup on the error side). Filed as P2a.
- **The relation fact store is off-network** (M-lens + S-lens, independently):
  facts are a `make-parameter` copied per-query into a fresh fork behind a
  *name-grained replace* merge. So real `:from` (dynamic fact loading) =
  migrating to a persistent fact-grained cell — which **is the same "deeper
  relational fact representation" the owner named as the SQLite prerequisite.**

The two P/R reviewers *conflicted* on D2's premise (is schema metadata
runtime-readable?); resolved by direct read (`macros.rkt:534/768/776`):
dual-written param+cell, Racket-runtime-readable, not Prologos-exposed → D2
premise corrected. And (S-lens) validation of runtime-parsed data is
**parsing, not type-checking** — so "validate via the type-checker" is a
category error.

**P3 "split the diff"** (owner): the demo builds a *scoped first slice* of real
on-network `:from`; the full competitive fact-representation work spun out as the
owned **RPF track** (Relational/PM, multi-track). Governance fix (P-lens): the
enabling fixes get owned-series tracks + deployment gates, not "filed somewhere."

### 3. P0 — runnable acceptance core (commit `282b138c`)

Opened P0 with a **6-facet syntax-grounding workflow** whose facets *ran live
`process-file` probes* (ground truth, not inference). Wrote the acceptance demo
`examples/dependency-demo/dependency-resolver.prologos` + synthetic dataset.
**Runs 0 errors / ~30s at L3**, results hand-verified: real file IO, pure-Prologos
CSV parse, relational graph queries + recursive closure + audit join (subquery
reuse), `explain` provenance, schema-as-maps, session+spawn.

P0's payoff was **5 filed gaps** — the demo's runnable core is much smaller than
the design assumed:
1. schema-typed `defr R : Schema` unwired at L3;
2. `require [core::csv]` E2001 at module load;
3. user `data` ADT constructors don't bind at WS L3 (→ P1 models JSON as maps);
4. top-level file IO works only as a bare expression (`def x := [read-file p]` → E2001);
5. `solve` returns per-derivation-path bindings (diamond → dups).

### 4. Schema-typed `defr` — gap #1 FIXED (commit `fac8902e`)

Grounding workflow → root cause: `parse-defr` never recognized `: Schema`; it fed
the bare `:` token to `parse-rel-params`, which errored, and the **file merge
silently dropped the error** → the relation never registered. The `surf-defr`
schema field + elaborator→relation-info threading were already wired.
- **parser**: `parse-defr-schema-typed` recognizes `: Schema`, derives arity +
  field-named params from the registered schema (arity drives both fact-row
  splitting and query matching).
- **driver**: `check-relation-schema-rows` type-checks each fact row positionally
  against the schema field types (reusing `schema-field-type->expr` + `check`).
- Tests `tests/test-defr-schema.rkt`; demo now uses `defr package : Package` and
  joins it in the audit query.
- Scope = register + type-check **facts**; field-named result projection +
  schema-typed **rules** deferred.

## Design decisions (the why)

- **`schema` as connective tissue** — the unifying narrative that makes the demo
  cohere (one `schema` typing both records and relations), not three disconnected
  pieces.
- **Seam-first** (owner) — deliberately drive into the gaps to *collect* them,
  per the stated goal ("identify where more work is needed").
- **Software dependency graph dataset** — on-theme with the owner's
  capability/supply-chain work; graph-shaped so subquery-reuse is natural.
- **P3 split-the-diff** — a scoped on-network slice now; the foundational
  competitive fact-representation as the owned RPF track (= SQLite prerequisite).
- **Validation = parsing, not type-checking** (D2 corrected) — runtime-parsed
  data isn't a compile-time type; needs a `Validation` accumulating applicative.
- **Schema-typed `defr` scope** — register + type-check facts (the demo's need);
  field-named projection + rules are honest follow-ons, not silently skipped.

## Surprises

- The critique caught **two blocking defects before implementation** — exactly
  what an adversarial cycle is for.
- The relation store being off-network *converged* with the owner's own SQLite
  instinct (the demo found the prerequisite they'd already named).
- **P0's runnable core was much smaller than the design assumed** — the whole
  ingestion→relation bridge is unbuilt at L3. Good: that's the dogfooding payoff.
- The suite failure was **Emacs lock files**, not the obvious suspect (foray).
- The LSP corruption was **stdout pollution from a top-level `println`**, not the
  perf-counter noise (those already go to stderr).
- `_` was a **`surf-hole`** (the partial-application placeholder), not a logic var.

## Lessons

- **The demo-as-forcing-function works.** In one session it surfaced and *fixed*
  real gaps: schema-typed `defr`, the `_` wildcard, the LSP framing bug, a test
  robustness bug. The runnable artifact is the diagnostic instrument.
- **Grounding workflows with live probes beat inference.** Facets that actually
  ran `process-file` gave ground truth; the acceptance file ran first-try because
  every form was probed.
- **Diagnose, don't assume** (recurring): the test failure wasn't foray; the LSP
  bug wasn't the perf-counters; `_` wasn't a `surf-var`. Each obvious suspect was
  wrong; the fix came from reading the actual path.
- **Adversarial critique before code pays for itself** — the `Validation` and
  off-network-store findings would have been expensive mid-implementation pivots.

## Carried forward

- **foray type-check hang — HUNTED + ISOLATED + worked around** (commit pending).
  Bisected to a **union-type non-convergence bug**: `<Int | String>` in a specific
  ORDER-DEPENDENT sequence (`def x : <Int|String> := 42` → `x` → `the <Int|String>
  "0"`) makes the typing propagator network never quiesce (infinite BSP firing in
  `attribute-map-merge-fn`, the `:type`-facet union join not reaching a fixpoint).
  Reordering avoids it; plain types are fine; each form alone is fine. NOT foray's
  fault — foray just triggers it. Commented foray's union forms (foray now loads:
  `--- 4 errors ---`, its own experimental bugs, no hang). Filed in DEFERRED.md
  ("BUG: Union-type checking hangs the type-checker") — needs a dedicated
  type-lattice-convergence fix + likely a fuel bound on the typing network so
  non-convergence is a bounded diagnostic, not a hang.
