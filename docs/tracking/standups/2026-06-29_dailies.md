## The arc (chronological, with the *why*)

### 1. Opening + grounding (4 parallel read-only agents)

Owner wants demos that exercise Process + Relational together: read CSV + a JSON
array of records (Process/IO), schema-validate them (`schema`), and query them
relationally with reusable subqueries over a graph; plus showcase *session-type
composition* (a session type in another's continuation). SQLite deferred until
sub-process infra + a deeper relational fact representation exist.

Rather than design from memory, grounded the *actual* state via 4 HEAD-pinned
agents (Process/IO, `schema`, Relational, session types). Headline:
- **The 3-paradigm table** (`RELATIONAL_LANGUAGE_VISION.org:13`) is the organizing
  insight: `schema` is the **relational "spec"** (the signature that types a
  relation's columns), and `session`/`defproc`/`proc` are the Process column. So
  the demo is "exercise all three columns at once," with `schema` as the
  *connective tissue* (it types both the records and the relations).
- CSV module exists (FFI to `io-ffi.rkt`); **no user-facing JSON parser**; IO is
  thin; the relational engine (`defr`/`solve`/recursion/joins) is solid; session
  basics run at L3, composition is partial.

### 2. Stage-3 design — D.1 → D.2

Wrote D.1 (the dependency-resolver demo concept), captured owner decisions
(D1–D7), then ran an **independent P/R/M/S critique cycle** (4 adversarial
reviewers). The critique earned its keep — it caught **two blocking defects
before any implementation**:
- **`Result` short-circuits** (S-lens): stdlib `Result.map2` stops at the first
  error; validation that should accumulate ALL field errors needs a `Validation`

The two P/R reviewers *conflicted* on D2's premise (is schema metadata
runtime-readable?); resolved by direct read (`macros.rkt:534/768/776`):
dual-written param+cell, Racket-runtime-readable, not Prologos-exposed → D2
premise corrected. And (S-lens) validation of runtime-parsed data is
**parsing, not type-checking** — so "validate via the type-checker" is a
category error.

**P3 "split the diff"** (owner): the demo builds a *scoped first slice* of real

### 1. Source-file-relative `read-file` paths (commit `81097db9`)

**Bug**: loading the demo in the editor REPL, a relative `read-file` path *doubled*
(`<repo>/…/dependency-demo/` + `racket/…/deps.csv`). Worked via `run-file.rkt`, not the LSP/REPL.

**Root cause**: `read-file` → `file->string` resolves against Racket's `current-directory`, and
**nothing in the compiler ever sets it** — purely ambient process CWD. `run-file.rkt` runs from
repo root (works); the editor launches the LSP/REPL with CWD = the file's dir (doubles). Modules,
by contrast, resolve location-independently against an absolute lib root (`driver.rkt:143`) —
resource files were the odd one out.

**Decision (owner)**: source-file-relative semantics. `process-file` absolutizes its path then
parameterizes `current-directory` to the source dir; `#:source-dir` override for callers
processing a copy (LSP diagnostics temp file); the REPL `loadFile` path parameterizes from the
doc URI. Demo uses sibling `"deps.csv"`. Regression test `tests/test-relative-path-resolution.rkt`.

**Surprise**: the doubling is NOT our code anchoring at the file dir — our code never touches
`current-directory` at all. It's the *editor* launching the process with CWD = file dir.

**Lesson (recurring, 2× this session)**: changing an exported signature (`process-file` +
`#:source-dir`) invalidates the `.zo` of EVERY dependent — must `raco make` ALL entry points
(`run-file`, **`repl.rkt`**, `lsp/server`), not just the ones you test. Missing `repl.rkt` →
Emacs REPL crashed with a linklet mismatch on relaunch. After an export-surface change,
recompile the entry-point graph, not just the module.

### 2. REPL ≠ `process-file`: schema-typed `defr` (FIXED — commit `aeda051d`)

**Symptom**: the demo runs 0 errors via `process-file`/`run-file.rkt`, but the LSP REPL
(`loadFile` → `eval-in-session` → `process-string-ws`) reports 1 error and the schema-typed
`package` relation never registers (`Unknown relation: package` at `solve`).

**Root cause (definitively pinned, via a repro harness)**: `process-file` uses the **merge**
pipeline; the REPL uses the **cell** pipeline (`extract-surfs-from-form-cells`). There,
**`schema` is mis-categorized as side-effect-only** (`form-cells.rkt:289`) — but `schema`
actually emits a type def `(def Name : (Type 0) (Type 0))` via the **whole-program** preparse
expander (`macros.rkt:2742`). The cell path discards it → the type `Package` is unbound → the
schema-typed `defr`'s `surf-var Package` can't elaborate → the `defr` command is **silently
dropped** (no residuation in the string path to recover). General gap: *any* `schema` use in the
REPL is affected, not just schema-typed `defr`.

**Design choice (owner)**: fix it properly in the cell path (**option A** — teach the cell
pipeline to emit schema's type def), over routing `loadFile` through `process-file` (option B).
Scope grew from "wire `defr`" to "fix schema def-emission in the cell pipeline" — broader but
more valuable (fixes schema-in-REPL generally).

**Fix (commit `aeda051d`)**: `form-cells` now emits the schema's `(def Name : (Type 0) (Type 0))`
in the cell pipeline (it was mis-categorized as side-effect-only). Simpler than factoring the
whole-program expander: emit the main type def directly from the datum's `cadr` — no re-parse, no
re-register, no datum-shape risk (the fields are already registered by preparse-expand-all).
Verified: `process-string-ws` output now identical to `process-file` (untyped + typed); the full
demo runs 0 errors via the REPL path; new regression test in `test-defr-schema.rkt` exercises the
`process-string-ws` path. Full suite **8388**, all pass. Nested sub-schema defs in the cell path
remain a follow-on.

**Surprises**:
- The **parse was fine** — `parse-datum` produced a correct schema-typed `surf-defr` (arity 3,
  field-named params); the failure was DOWNSTREAM at elaboration (unbound type), not in parsing.
  The cell path *does* route `defr` through `parse-datum` (via `parse-eval-tree-for-cell`),
  despite `parse-defr-tree` being a stub.
- The failure was **silently dropped** — `form-cells.rkt:302-304` drops error surfs with no
  diagnostic; the only visible error was downstream at `solve`. Silent drops mask bugs.

**Lessons**:
- **Diagnose, don't assume** (hard-won here): three fix attempts failed because I hypothesized
  before confirming (init-parity; routing schema to the datum branch). Only the **instrumented
  repro** (printing `process-command`'s `defr` arm) gave ground truth — the arm is reached for
  untyped but NEVER for schema-typed in the string path.
- **A reproduction harness beats reading code**: `scratchpad/repro-repl-divergence.rkt`
  (process-file vs process-string-ws × untyped vs typed) was the decisive instrument.
- **Two-context boundary, again**: features wired in ONE parser path don't auto-work in the
  other. The schema-typed `defr` feature (`fac8902e`) only taught the **preparse** parser; the
  cell pipeline never got it. The `process-file` (merge) vs `process-string-ws` (cell) split is a
  standing divergence source — **validate new user-facing features at L3 via BOTH `process-file`
  AND the REPL/`process-string-ws` path**, not just `process-file`. (Watching: candidate for a
  testing-rules addition once it has 2-3 data points.)
