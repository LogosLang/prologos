### Semaphore floor reproduced; raw-memory handoff is ~60 ns — no commit (2026-10-12)
- **Why / decision**: before designing any FFI primitive, measure the thing the
  record didn't: a handoff that never sleeps. Probe `pingpong.rkt` — A/B threads,
  200 k round-trips, three mechanisms, same protocol.

  | mechanism (two `#:pool 'own` threads) | ns / one-way hop |
  |---|---|
  | `semaphore-post` → `semaphore-wait` | **7 302** (= the record's ~8 µs) |
  | spin on `box` + `box-cas!` + fences | 68 |
  | spin on `box` + `set-box!` + fences | 67 |
  | same, orchestrator also a parallel thread | 58 |
  | `box-cas!` + fence, same thread | 2.3 |

  **Decision**: the FFI premise is dropped for the *signal*. Racket CS compiles
  `box-cas!` and `memory-order-*` to native CAS/`dmb`; a C library sits on the
  same hardware floor. (FFI stays relevant for a different reason — see the
  allocation entries.)
- **Surprise / correction**: the 2B "spin-poll catastrophe" (2 400 µs, design
  doc Approach 4) has a plain cause: it polled `semaphore-try-wait?` — a
  rumble-scheduler object — from the main thread. Every mechanism in the 2B
  table routes through the scheduler; a box with fences does not. Also: the main
  Racket thread is measurably slower at the same loop than a parallel thread
  (engine ticks) — put the orchestrator on a parallel thread.
- **Next**: fan-out + barrier at K, with and without allocation.

### K-way fan-out ~1.8 µs/round; allocating work goes 9× SLOWER in parallel — no commit (2026-10-12)
- **Why / decision**: `fanout.rkt` — generation box dispatch, CAS-counter
  barrier, K=8. Zero-work round: **1.7–1.9 µs** (vs ~80 µs in the record; not
  8×60 ns because 8 cores bounce one counter line). With ~1000 conses per
  worker per round: **67 µs parallel vs 7.3 µs sequential**; K=16: 208 vs 15.5.
- **Surprise**: the handoff cost was hiding a second, independent ceiling.
  Isolation (`alloc.rkt`, `scale.rkt`), same total work, 8 threads vs sequential:

  | work | speedup |
  |---|---|
  | pure fixnum compute | 8.3× (16 threads: ~16×) |
  | `unsafe-vector-set!` into pre-allocated per-thread vectors | 8.0× |
  | 1 cons per 64 iterations | 6.7× (GC = 26 of 34 ms) |
  | cons-heavy lists, parallel threads, no sync at all | ~1.2× |
  | cons-heavy, 8 **places** (`places.rkt`) | 0.8× |
  | cons-heavy, GC disabled (`collect-trip-bytes` 1 GB → 0 ms GC; `gctune.rkt`) | ~0.9× |

  A single parallel thread doing all the work alone is *faster* than the main
  thread (22 vs 36 ms) — the threads are fine; the combination isn't.
- **Mechanism (verified in source, not conjecture)**: Chez `c/alloc.c`
  (Racket's fork, Debian mirror of 8.7): `S_get_more_room_help` and
  `S_find_more_gc_room` take `alloc_mutex_acquire()` on every refill of a
  thread's allocation area, plus `S_scan_dirty` and a possible collector queue —
  so allocation serializes at segment granularity under a global mutex, and
  each GC must rendezvous all threads. Places share the collector and the mutex.
  Large objects (`make-fxvector 1000`) are *worse* in parallel than sequential
  (44 vs 17 ms) — they bypass the thread area and hit the mutex per object.
- **Next**: is the ceiling a wall or a curve? Sweep intensity.

### Scaling is a function of allocation intensity; the solver is allocation-bound — no commit (2026-10-12)
- **Why / decision**: two probes. `alloc-per-fire.rkt` measures the REAL network
  and solver with `(current-memory-use 'cumulative)`; `intensity.rkt` sweeps a
  synthetic cons-every-N-ops workload across K.

  Real solver (sequential, per op):

  | op | bytes | ns | bytes/µs |
  |---|---|---|---|
  | one light BSP fire (N=8 / N=64 per round) | 2 764 / 3 111 | 1 832 / 1 513 | 1.5–2.1 K |
  | DFS 3-clause query | 7 129 | 2 952 | 2.4 K |
  | ATMS 3-clause query | 58 494 | 27 666 | 2.1 K |
  | DFS 16-clause | 35 067 | 14 874 | 2.4 K |
  | ATMS 16-clause | 192 172 | 90 098 | 2.1 K |
  | DFS / ATMS 8-fact (Tier 1) | 2 640 / 1 142 | 1 433 / 993 | 1.8 K / 1.1 K |
  | `net-cell-write` (replacement merge) | 480 | 153 | 3.1 K |
  | `net-cell-read` | 0 | 15 | — |
  | `fork-prop-network` | 1 233 | 232 | 5.3 K |

  **Key finding**: wall time ≈ bytes ÷ 2.2 GB/s on every row. The 2B result
  "DFS 6–11× faster than ATMS" is reproduced and *explained*: ATMS allocates
  8× more bytes per query. The solver's speed, sequential or parallel, is its
  allocation volume.

  Synthetic intensity sweep (`intensity.rkt`, speedup vs K=1, same total work):

  | bytes/µs at K=1 | K=4 | K=8 | K=16 |
  |---|---|---|---|
  | ~1 050 (cons every 1–4 ops) | 3.1–4.2× | 3.1–3.7× | 2.8–3.0× |
  | ~860 | 3.5× | 4.1× | 5.9× |
  | ~500 | 4.8× | 7.4× | 6.4× |
  | ~180 | 4.2× | 7.6× | 11.8× |
  | ~45 | 4.3× | 7.6× | 11.5× |

  The solver at ~2 KB/µs is *above* the top row → expect **≤3× on any K** with
  today's representation, which is the whole 2B outcome in one number.
- **Decision**: the design question is no longer "which concurrency primitive"
  but **"how many bytes does a fire allocate."** Lowering bytes/op is the one
  lever that improves sequential time AND unlocks parallel scaling — the two
  problems are the same problem. Direction (conjecture, to be tested in PSF-2/3):
  per-PU flat arenas (`fxvector`/`bytes`, mutation in place — the 8.0× row is
  the existence proof) with allocation only at fork/commit boundaries; the WAM's
  heap/stack/trail answer, propagator-native. Mutation-in-place inside a PU is
  consistent with the mantra: the PU is the unit of monotone information flow;
  its internal arena is representation, not semantics.
- **Surprise / correction**: I had estimated Racket CS foreign-call overhead at
  "~100+ ns"; `ffi-futures.rkt` measures **8.4 ns** for `_int -> _int`, 19 ns
  for `memset` on a `bytes`, 7.9 ns from a parallel thread. The boundary is
  cheap; a C kernel over flat memory is viable at ~10–20 ns per crossing. It is
  still *second* in order — a flat Racket kernel has the same scaling and no
  boundary — but it is no longer disqualified by crossing cost. Futures:
  `future`+`touch` = 4.8 µs; same allocator ceiling (cons 33 vs 41 ms).

### Executor = (core, arena): the owner's scheduler framing measured at 5.8× (K=8) / 9.9× (K=16) — no commit (2026-10-12)
- **Why / decision**: owner's reframing — *parallel search as scheduler
  technology; per-core executors as children of the scheduler.* Holds for the
  dispatch cost (that IS the spin-pool: persistent executors owned by the BSP
  scheduler, spinning while a solve is active). The remaining per-core cost is
  not a scheduling cost — it is one shared Chez heap behind one mutex — so the
  framing needs one ingredient: **an executor owns memory**. Executor =
  (core, arena); a fire is mutation-in-place in its arena; cell merge is a
  lattice join (commutative, associative, idempotent), so per-executor local
  accumulation followed by a global join reaches the same fixpoint as any
  sequential order — the CALM/LVars argument applied to the scheduler's
  partition. The join is not a serial phase: each executor joins its own dirty
  list into canonical with CAS-max (concurrent joins commute). Probe family
  `arena-exec*.rkt` (K spinning executors, fxvector delta arenas, canonical
  vector of fixnums, two barriers per round: fire, join).
- **Key finding** (F=1024 trivial fires/executor/round, C=16 384 cells):

  | variant | K=1 | K=8 | K=16 | aggregate at K=16 |
  |---|---|---|---|---|
  | dense delta scan join (`arena-exec.rkt`, F=64) | 47 ns/fire | 15 ns | 11.6 ns | 86 k fires/ms |
  | dirty-list CAS-join (`arena-exec3.rkt`) | 10.8 | 5.0 | 3.3 | 302 k |
  | + 90 % locality partition (`arena-exec4.rkt`) | 11.6 | 4.2 | 4.0 | 250 k |
  | + padded per-executor counters (`arena-exec5.rkt`) | **11.1** | **1.9 (5.8×)** | **1.1 (9.9×)** | **890 k fires/ms** |

  Per-round wall at K=16 is 18 µs vs 11 µs at K=1 for 16× the fires. Steady
  state allocates nothing. Against today's light BSP fire (1.5 µs, 2.8 KB): the
  fire here is trivial (3 reads + a max), so the ~1000× is NOT a solver
  prediction — the *shape* is the result: arena fires + lattice join + spin
  executors scale near-linearly where heap fires cap at ≤3×.
- **Surprise / correction** — three defects found in my own probe, each a
  design lesson for the real thing: (1) a dense per-executor delta makes the
  join O(K·C) — join cost grew with K; dirty lists fix it; (2) random access to
  one shared canonical arena bounces cache lines (true + false sharing: 8
  fixnum cells per 64-byte line) — partition for locality, as Pregel/GraphLab
  do; (3) K consecutively-allocated `box` counters share cache lines — padding
  the hot per-executor words took K=8 from 2.9× to 5.8×. Expect all three in
  the real design; (3) means per-executor state must be its own object, never
  a slot in a shared vector of boxes.
- **Next**: PSF-2 census stands (what to put in the arena). PSF-3 should now be
  the arena executor with a *real* lattice merge (e.g. the type-lattice join or
  a tagged-entry bitmask write) in place of `max`, to get a solver-relevant
  ns/fire. Open theory question for the design doc: the partition is the
  stratum-0 topology — can the scheduler derive it from the propagator graph
  (cell ownership = graph cut), so locality is structural rather than tuned?

### PSF-2 — allocation-site census of one BSP fire: half is ceremony, every write is paid twice — no commit (2026-10-12)
- **Why / decision**: the arena design has to absorb the right bytes first.
  `census.rkt` measures pieces by subtraction on the real network
  (`current-memory-use 'cumulative`), Racket 9.3.

  | piece | bytes | ns |
  |---|---|---|
  | `champ-insert`, replace, N=16 / 256 / 4096 | 352 / 612 / 896 | 51 / 79 / 99 |
  | `champ-lookup` (any N) | **64** | 36–55 |
  | `struct-copy prop-cell` | 64 | 4 |
  | `struct-copy prop-network`+`warm`+`hot` | 96 | 10 |
  | `net-cell-write`, 0 / 1 / 8 dependents | 481 / 529 / 801 | 183 / 202 / 286 |
  | `net-cell-write`, no change | 0 | 56 |
  | BSP, per read-only fire (slope 8→64) | **1 386** | ~570 |
  | BSP, per read+write fire (slope 8→64) | **2 819** | ~1 500 |

  So a light read+write fire ≈ **1.4 KB scheduler/fire ceremony (50 %) +
  0.5 KB the write (17 %) + 0.9 KB re-merging the fire's result into the
  canonical (33 %)**.
- **Key finding — the shape, from `propagator.rkt:2855-2959` +
  `2966-3056`**: the BSP protocol is *fire on a snapshot → the fire returns a
  whole new network (its `net-cell-write` already path-copied the CHAMP and
  the 3-struct spine) → `parameterize` ×2, `for/hasheq` output-set,
  `champ-diff` snapshot-vs-result (lists + closure), `fire-result` struct →
  `bulk-merge-writes` calls `net-cell-write` on the canonical AGAIN*. Every
  written byte is paid twice, and the bookkeeping around the two writes costs
  as much as both. This is not waste in the code — it is the price of
  "network as persistent value + fires that return networks". The arena
  executor dissolves exactly this: a fire writes into its executor's delta (no
  copy, no diff — the dirty list IS the diff), and the join is the single
  write. PSF-2's prediction for PSF-3: an arena fire path should land near
  **the write alone (~0.1–0.2 KB, ~100 ns) or below**, i.e. 10–20× fewer
  bytes per fire, which by the intensity law (~2 KB/µs → ≤3×; ≤0.2 KB/µs →
  ~12×) is what unlocks the parallel scaling as well. Conjecture until
  measured on a real lattice merge.
- **Cheap sequential wins noticed, not acted on** (DEFERRED candidates):
  (a) `champ-lookup` allocates 64 B per call — a read should allocate 0;
  at ~5 lookups per fire that is ~10 % of a light fire's bytes. (b)
  `fire-and-collect-writes` builds a `for/hasheq` output-set per fire even for
  single-output propagators; (c) two `champ-fold`s over dependents in the
  slow write path allocate closures per write.

### PSF-3 — arena executors on the REAL tagged lattice: same fixpoint at every K and in async mode; 12–16× per fire, >100× fewer bytes; scaling capped by memory, not by software — no commit (2026-10-12)
- **Why / decision**: PSF-2 predicted an arena fire path at ≤0.2 KB and ≥6× at
  K=8. `arena-tagged{,2,3}.rkt` express `tagged-cell-value`
  (`decision-cell.rkt:397-500`: base ⊔ by domain merge × entries as a set under
  union; read = entries ⊆ worldview, merged) as a fixed-stride flat record
  `[base, n, flag, (bm,v)×E]` with in-place join, C=16 384 cells, P=16 logical
  partitions (fixed, so every K runs the IDENTICAL fire set), K executors owning
  P/K each, dirty lists bucketed by owner (no CAS, no contention), and a
  fixpoint hash (per cell: base + sorted entries) compared across K.
  **K** = number of executors = persistent `#:pool 'own` threads owned by the
  scheduler [owner asked]; per-executor timings were uniform (K=16 fire
  82–107 µs across all sixteen) → no core-class effect at this scale; K should
  be a scheduler cell, default ≈ cores − 2 (orchestrator + main thread), never
  oversubscribed (a descheduled spinner holds the barrier a whole quantum).
- **Key findings**:
  1. **Semantics**: fixpoint hash identical for K ∈ {1,2,4,8,16}, in BOTH the
     buffered (BSP: write delta → barrier → owner joins) mode and the DIRECT
     mode (owner writes its own canonical records during the fire phase;
     append-only, entry words → `memory-order-release` → count; readers
     count → `memory-order-acquire` → entries). Quiescence test on a pure
     max lattice: BSP converges in **15 rounds, DIRECT in 10** — information
     crosses the network within a round. This is Cousot's chaotic iteration /
     Bertsekas' asynchronous fixpoint, tested: monotone + fair ⇒ same lfp.
     Caveat recorded: a fixed-round, non-quiescent, non-idempotent workload
     gives schedule-dependent INTERMEDIATE states under DIRECT (hashes
     differed) while BSP gives deterministic ones — if any ATMS/worldview
     logic depends on round-synchronous visibility, that is a design
     constraint to surface, not a bug.
  2. **Per fire, data-structure level** (same semantics, 10 rounds, ~10
     writes/cell): heap `tagged-cell-value` + `make-tagged-merge`, delta-
     wrapped as `net-cell-write` does: **172–178 ns, 187 B**. Arena buffered
     K=1: **117–131 ns, ~0 B** (1–18 B/fire is orchestration). Arena DIRECT
     K=1: **95 ns** (join phase gone: 2× sequential gain by itself). Against
     today's full network fire (PSF-2: ~1 500 ns, 2 819 B): **12–16× time,
     >100× bytes**. Prediction "≤0.2 KB": ✓.
  3. **Scaling**: ~4× at K=4 in every mode; **3.9–5.5× at K=8–16** (buffered
     K=16: 18.8–27 ns/fire, 36–53 k fires/ms; DIRECT K=16: 9.9–11 ns/fire,
     91–100 k fires/ms, 8.7× over K=1 in the fixed-round run). Prediction
     "≥6× at K=8": **✗ on this workload**. Cause, from per-executor timing:
     per-executor cost rises with K on purely LOCAL data (join 62 → 122 →
     230 ns/cell at K=4/8/16; fire 80 → 95 → 130 ns) — the cluster-shared
     L2 / fabric under all-core memory streaming (~430 B per joined cell at
     E=12) — plus 2× straggler spread in join time (the round waits for the
     max). These fires are trivially light (3 reads + a max); real fires are
     10–50× heavier, and `spinpool.rkt` showed 6.2× at K=8 / 9.4× at K=16
     once per-worker work reaches ~12 µs. So this is a LOWER bound on scaling
     and an UPPER bound on per-fire savings. Lever if needed: compact records
     (most cells carry ≤2 entries; E=12 is 216 B/cell → overflow side table).
  4. **Latent quadratic found**: `tagged-cell-write` conses and
     `tagged-cell-merge` appends — entries are never deduplicated, so a
     read costs O(#writes ever made to the cell). Invisible today because
     solver cells are query-scoped; the heap baseline at 100 rounds did not
     finish in 300 s. → DEFERRED candidate.
- **Surprise / correction** (three harness bugs, each a lesson): (a) P must
  be divisible by K or the verification hash catches it — it did; (b) my
  heap baseline first called `(merge old (write old …))`, duplicating entry
  lists exponentially — the real `net-cell-write` wraps a DELTA
  (`propagator.rkt:2014-2019`) precisely to avoid this; (c) convergence
  detection must count CANONICAL changes only, never delta writes.
- **Design shape now supported by measurement** (conjecture → candidate):
  the scheduler owns K executors; executors own partitions (= a cut of the
  propagator graph); S0 fires write their own partition's records directly
  (chaotic iteration, no barrier inside S0); cross-partition writes go via
  owner-bucketed deltas; **the barrier IS the stratum boundary** — S(-1)
  retraction and S1 NAF, the non-monotone strata, are exactly where
  round-synchronous visibility is required, and `stratification.md` already
  puts them there. Phases collapse where everything is monotone; the
  non-monotone boundary is where the barrier lives. That is the mantra's
  sentence, measured.

  sweep (10 / 100 / 1 000 ns of real term work per fire) on the DIRECT arena
  to pin the K-scaling curve at realistic fire weight before designing.
